# 08 — 移植理念与未决问题

这不是对现状的描述，是**约束**。它决定后面所有设计取舍，也决定哪些东西
**不做**——包括那些"加上去也无妨"的选项。

---

## 1. 理念

**DeepSeek Harness 的 agent 设计是好的，我们要把它搬到 Android 上。**
但用户群体的需求、系统本身的封闭性、以及移动端设备的定位，决定了必须加一层
**硬性限制**：限制读写、限制程序执行。

限制的**目的不是免责**。是：

> **借用设备的性能资源，同时隔离文件系统。**
> **不以脱责为目的，要追求用户体验和安全性。**

三条推论，每一条都排除了一类做法；另有一条关于花钱的规则：

### 1.1 不提供 "full access" 这类选项

不是"默认安全、高级用户可解锁"，而是**根本不设这个开关**。

理由不是"用户会选错"，而是更硬的：**一个可提升的权限层级，本身就是一个攻击面。**
提示注入不需要用户点错，它只需要**说服模型去要**更高的权限。而"要权限"这件事，
在 DSH 的模型里是**一等公民**——它有 `permission/preset`、`sandbox/mode`、
`approval/policy` 三类持久事件，就是权限模式切换留下的记录。

对照实测：DSH 自己的沙箱会**降级**。它的文档写着，沙箱启动失败时默认**不加沙箱运行**，
除非显式配置。那条"逃生舱"就是本节要排除的东西。

**所以：能力在对话创建时确定，运行期不能提升。** 没有"要更多权限"的路径，
因为不存在更多权限可以给。

**持续会话不是这类模式。** 它不提供任何可提升的能力层级，只改变"这一次请求带什么"：
工具、审批、SSH 授权和工作区边界都不变。唯一新增的 `recall` 工具只读当前对话的
记录、本地、不联网、不写任何东西，因此不需要新的"一句话例外"；理由见
`docs/06-agent-loop-ui.md` 的 "Continuous sessions" 与 `docs/07-gotchas.md` A24。

### 1.2 能力边界要能被一句话说清

现有实现有一个对的方向：`requiresOptIn` 那类标注迫使调用方显式承认能力，
而**助手（assistant）本来就带一个工具清单**（`toolsJson`）。
这说明"能力是助手的属性"这个想法已经有了实现基础。

用户要能读到的话不是"ask / never / full access"，而是：

> **代码在你的设备上运行，只看到你给它的东西，连不出网，也碰不到你的文件。**

这句话必须是**真的**，而且**不因设置而变**。实测支持它：官方沙箱里
`fetch`、`require`、`process` 全是 `undefined`——**网络是平台切断的，不是我们加的墙。**

有一条例外不在 agent 的能力里，而在用户的操作里：Files 的 **Download from a URL**。URL 由用户输入，文件落到工作区或用户通过 SAF 选择的目录；app 不因此获得
通用存储权限，**工具目录里没有这个能力，agent 也调不到它**。它打开的是用户的手，
不是模型的路。除此之外，能离开设备的仍然只有以下几类：SSH 工具、用户主动选择的付费
web 工具、**用户显式打开、由 app 代发的只读内容源**（`bili_search` 等 B 站只读工具，
以及本机搜索 `web_search_local`，见 §1.7）、**用户显式打开、按对话授权的 URL 下载**
（`download_url`，见 §1.6），以及**用户显式打开、按对话授权的本机网页抓取**
（`web_fetch_local`，见 §1.7）。

**B 站只读不是新例外，是「应用代助手读外部内容」这一类的新成员。** 它和
`web_search` / `web_fetch` 同形：请求由 app 发出，助手自身仍然没有网络，工具参数
只有 BV/cv/ss/ep 号、mid、房间号或关键词、没有 URL，也没有任何以用户身份写入或
发布的能力。来源免费、没有可配置的 key，所以"用户选择了这个来源"由 Settings 的
全局开关表达，而不是由配置密钥表达。匿名可读的范围（搜索、视频信息、相关推荐、
评论与楼中楼、专栏、UP 主主页、榜单/热门/热搜、番剧信息、直播间状态、弹幕抽样）
都不需要账号，因此也不增加新的凭据类别；关闭时这些工具从请求、选择器和
`unavailable_tools` 里**消失**，不是灰行；开着时还要在助手里显式勾选（`optIn`），
因为 `null` 的"全部"早于这些名字。它因此不需要 §1.2.1 的会话授权：没有远端写入、
没有凭据、没有不可逆的动作。它读回的内容是不可信第三方文本，提示注入的风险和
`web_fetch` 属于同一类，由工具描述里的警告和输入侧的"素材不是指令"共同约束，而
不是由权限系统解决。

**可选登录是凭据类别的增加，不是新的能力例外。** B 站匿名读不到视频语音（字幕列表
为空、AI 总结返回 -101），所以设置里可以扫码登录，且只用于"需要登录才能看的公开
内容"：字幕、B 站自己的 AI 总结、第 2 页以后的评论。只保存读接口需要的
`SESSDATA` 和 `DedeUserID`，**不保存 `bili_jct`**（写/CSRF 令牌，本产品没有写路径）；
按 OAuth token 同级的规则处理——`SecureStore`、不进备份、不进诊断、随时可断开；
未登录时那个工具（`bili_transcript`）在请求和选择器里**不出现**。它不读历史、
收藏、关注或私信：那些是账号数据，不是公开内容，会改变产品承诺，需要单独决策。

**工作区类型不是权限层级。** `workspaces.kind`（schema v29）标记唯一的内置工坊，
只决定这个工作区里的非场景对话获得哪些**由宿主追加、没有能力的辅助工具**：RP 的
`rp_format`、`rp_validate`、`rp_create_scene`，以及 app 配置的六个读取/草稿工具
（v29 把原来的两个工坊合成一个，v28 的 `roleplay` / `studio` 值由迁移改写）。
它和永久/临时一样是数据属性：不增加网络、文件、执行或写 app 状态的能力；有能力
的工具仍来自助手与对话自己的清单；模型没有任何工具可以创建工作区、进入工作区或
标记工作区——因此不存在"说服模型把我放进特权位置"的路径。这些辅助工具不在
`ToolCatalog` 里，也不出现在任何选择器、审批表或能力缺口报告里。这是它能不加第三个
例外就落地的原因；不变量见 `docs/07-gotchas.md` A31，设计见
`docs/proposals/workshop-merge.md`。

### 1.2.1 第一个被批准的例外：SSH，默认关闭，按会话确认

SSH 工具（`ssh_probe`、`ssh_list`、`ssh_read_file`、`ssh_exec`、`ssh_upload`、
`ssh_write_file`、`ssh_download`）打破上面那句话的两个部分：agent 可以连网，
也可以在**另一台机器**上读取文件、传输文件；只有显式选中 `ssh_exec` 时才会
执行任意命令。这是用户明确要求的能力，不能靠"文档里不写"解决。约束是：

- **默认关闭，且是两层关闭**：Settings 的全局开关默认关；即使打开，助手还必须在
  工具清单里显式选中要用的 SSH 族；第一次调用时，会话里再弹一次**能力授权**，
  不是普通的单次审批。工具清单按族呈现，SSH 被拆成**只读**（`ssh_hosts`、
  `ssh_probe`、`ssh_list`、`ssh_read_file`、`ssh_download`）和**执行/写入**
  （`ssh_exec`、`ssh_upload`、`ssh_write_file`）两个独立的族开关：打开只读不会
  顺带打开执行/写入，选中执行/写入这一族仍是一次显式动作，并且会话授权会按危险
  工具重新询问。族开关写进 `toolsJson` 的就是这一族的每个名字，不是 `null`
  （"全部"）——`null` 仍然不包含任何 SSH 工具。`toolsJson = null` 的历史助手
  **不会**自动获得 SSH——`ToolCatalog.permits` 对所有 `remote = true` 的工具特判，
  必须显式写进清单。
- **应用保存的是地址簿，不是凭据库。** 设置里可以有多台主机：别名、地址、端口、
  用户名、可选的主机密钥指纹。**不保存密码或私钥**，所以任何一次模型发起的调用都
  不可能用到用户存起来的凭据。整份列表放在 `SecureStore`（Android Keystore）
  的一个文档里，与 API key 一样不进入备份、不进入诊断日志——地址本身也是隐私。
- **每个对话勾选"把哪几台告诉 agent"，这是信息，不是权限。** `ssh_hosts` 是只读
  工具：不联网、不返回凭据，勾选只决定它的返回内容，改动下一回合生效，**不重置
  SSH 授权**——它没有授予任何东西，也就没有可撤销的授权。清单存在
  `conversations.sshHostsJson`，只有用户能改。
- **连接凭据由调用本身携带。** 工具收 `host`/`port`/`username`，加 `identityFile`
  （工作区里的密钥文件，经 `SessionWorkspace` 读取）或 `password`。密码或私钥文本
  会进入对话记录并发给模型服务商，工具描述和授权文案都写明这一点；工作区里的密钥
  同样能被 `read_file` 读到——那是工作区边界的一部分，用户放进去就是交给 agent 的。
- **为什么不解析别名。** 曾经的设计让 `host` 解析到 app 保存的主机并附上凭据，
  理由是"模型看不到密码"。但它把"把哪几台告诉模型"变成了"让模型用哪几把钥匙"：
  模型只要说对别名，app 就用用户从未在那一刻接触过的凭据登录。信息开关和凭据使用权
  必须分开，而分开的彻底做法是 **app 根本不持有可被工具使用的凭据**。
- **授权按会话持久化**，可撤销；全局开关关闭会清掉所有会话的授权。
  只读组合（`ssh_probe`、`ssh_list`、`ssh_read_file`、`ssh_download`）不经过
  任意 shell，可以在不选 `ssh_exec` 的情况下使用；`ssh_upload` 和
  `ssh_write_file` 是远端写工具。之后再加 `ssh_exec`、`ssh_upload` 或
  `ssh_write_file` 会重置该会话的授权，而不是沿用只读授权。
  授权后，后续调用回到普通 `ToolPolicy`（默认 Free），不再逐条询问。
- **会话工具集只由用户改，且从下一回合生效**。对话菜单里可以增删这个会话
  使用的工具；模型不能调用任何东西来改它，消息和工具结果也不能。候选范围是
  助手已有的工具加上这个会话已经有的工具，对话不能凭空获得助手从未提供的
  能力。放宽是用户勾选并点“应用”这一下，不是新的逐次审批；SSH 工具仍须显式
  选中（只读与执行/写入是两个独立的族开关，互不连带），并按 §1.5 走会话授权。
  编辑后保存的是显式清单，以后的版本新增工具不会自动进来。
- **传输安全仍在**：host key TOFU，标准 `SHA256:` 指纹，变 key 失败关闭；
  可显式给指纹。这不是权限限制，是防中间人。
- **风险在远端，不在工作区副本**：命令可以删数据、停服务、改权限，上传可以覆盖
  远端文件，且都不可撤销；下载把远端内容带进工作区，占配额，也可能带来提示注入。
  授权文案必须说清这一点，也必须说清粘贴的密码/私钥会进入会话并发给 DeepSeek；
  工作区里的 key 文件只在本地读取，但工作区文件可以被带到远端。

这不是"full access"模式：没有本地权限提升，没有可累积的权限层级，没有
"高级用户解锁"。它是一个**用户显式打开、按会话授权、可撤销的远程命令与文件
传输通道**。但它确实是对 §1.2 那句话的例外；当 SSH 关闭时（默认），原句仍然成立。
文档不再声称"任何设置下都连不出网"——只在 SSH 关闭时成立。

### 1.6 第二个被批准的例外：URL 下载，默认关闭，按会话确认

`download_url` 让 agent 让 app 去下载一个 https URL 到工作区。它和 Files 的
Download from a URL 做同一件事，区别是谁在按按钮：URL 由模型给出，请求由 app
发出。agent 自己仍然没有 socket、没有 DNS、没有网络栈，所以 §1.2 的"连不出网"
在结构上仍然成立；但它不再是**用户的手**，而是模型的路径，因此需要单独回答
§1.2.1 的框架问题：

- **为什么需要它。** 用户经常希望 agent 把某个链接变成工作区里的文件，然后继续
  用文档/文件工具处理——存一份 PDF、下载一个压缩包、把图片拉进来。手工"先下到
  系统下载目录再导入 Files"把一次对话变成三步操作。
- **它为什么不是 web_fetch。** `web_fetch` 返回网页正文，由付费后端打开页面，
  结果进上下文；`download_url` 保存**字节**到工作区，由 app 自己的 OkHttp 客户端
  请求，不经过第三方，也不把内容塞进上下文。
- **URL 不是中性的。** 这是这个能力唯一必须说清楚的风险：HTTP 请求的 path 和
  query 是任意字符串，攻击者的服务器会记录它们，返回 404 也照样收到。因此提示
  注入只要能让模型"把一段内容编码进 URL 再请求一下"，就有一条**免费、不限次数**
  的外传通道——`web_fetch` 已经具备同样的性质，但它付费、需要 key、次数有限；
  下载把这条通道变便宜了。写进 consent 对话框、写在工具描述里、写在 Settings
  的开关说明里，是披露，不是技术阻断。结构上可行的解法（只允许用户消息里的 URL、
  域名白名单）都被评估过，用户选择了灵活性与每对话授权。
- **三层开关，和 SSH 同形。** Settings 的全局开关默认关；关着时 `download_url`
  从每个 picker、请求、审批表和 `unavailable_tools` 里**消失**；打开后助手仍须
  显式勾选（`optIn`）；每段对话第一次调用弹专用授权，显示 URL 与 host，要求勾选
  "URL 可以把数据带出去"，允许写
  `conversations.downloadAllowed`，之后走普通 `ToolPolicy`。撤销入口在聊天菜单；
  全局开关关闭会清空所有对话的授权。改实战/新增工具不会重置它（没有第二个
  下载工具），但它和 SSH 一样是**能力授予**，不是 `needsApproval`。
- **硬限制。** 仅 `https`；只接受公网地址（私网/回环/链路本地/CGNAT/保留段
  一律拒绝，DNS 解析和每次重定向都重新检查——与用户下载共用同一套
  `DownloadUrl` 规则）；单文件 64 MiB；不覆盖同名文件，落在 `downloads/`；
  工作区配额、文件数和预留空间照常；GET-only，无 cookie、无凭据、无自定义头、
  无 POST。不执行、不解析下载的内容，工具结果只报告路径、字节数和 MIME。
- **诊断只记 host 和字节数。** URL 的 query 可能装着要外传的内容，记录整条 URL
  等于在本地日志里再泄露一次；工具层也不把 URL 写进日志。
- **它改变的那句话。** §1.6 让例外从一（SSH）变成二；§1.7 又加入第三个（本机网页
  抓取）。默认状态（三个开关都关）下原句仍然完全成立；打开 URL 下载后，"agent 能让
  app 在公网抓取它指定的 URL"成为用户选择承担的能力。`unavailable_tools` 在开关关闭
  时不会说出这个名字，和 SSH 一样，因为它不在全集里。

### 1.6.1 为什么不做成"只允许用户消息里的 URL"

这是评估过的结构性方案：工具只接受在用户消息里逐字出现过的 URL，模型无法构造
新地址，外传通道从根上关掉。它更符合"安全来自结构"，代价是 agent 不能下载搜索
结果里的链接，也不能按用户的自然语言描述自己拼 URL——"帮我下 GitHub 最新
release"必须先由用户贴链接。用户在两个方向之间选择了任意 URL + 每对话授权，
所以这里记录的是被否决的方向，避免下一个人把它当成没想过。

### 1.7 第三个被批准的例外：本机网页抓取（和同族的本机搜索）

付费 `web_search` / `web_fetch` 的请求由提供商发起：搜索结果是提供商的索引，
抓取结果受提供商所在位置、索引与合规策略限制。用户要求"像浏览器一样"从自己的
手机网络读网页，而这件事 App 自己做得到——这也是免费、无需 key 的来源。落地为
两个工具，门禁形状不同：

- **`web_search_local`（本机搜索）不是新例外。** 它只接一个 query，没有 URL，免费、
  匿名、只读，读的是 DuckDuckGo（默认）或 Bing 的公开结果页；门禁照 B 站工具：
  Settings 全局开关（默认关）+ 助手显式选择（`optIn`），开关关闭时从选择器、请求
  和 `unavailable_tools` 里消失。它没有每对话授权：关键词本来就属于 §1.2 第三类
  "用户显式打开、由 app 代发的只读内容源"。
- **`web_fetch_local`（本机抓取）是第三个例外。** 模型给 URL，App 在本机发请求，
  免费且不限次——这是 `download_url` 的同一条外传通道（见 §1.6），只是把字节换成
  正文；因此它照抄 `download_url` 的三层门禁：Settings 全局开关（默认关）、
  catalogue 的 `optIn`、每对话一次授权（`conversations.localFetchAllowed`，
  schema v30，`MIGRATION_29_30`）；聊天菜单可撤销，全局开关关闭清空所有授权。
- **硬限制**：仅 `https`、仅公网地址（DNS 解析时检查，每次重定向重新检查）、GET-only、
  无 cookie/凭据/自定义头、2 MiB/30 s、正文 20,000 字符；URL 校验与 DNS/重定向守卫
  和 `download_url` 共用同一份 `GuardedHttp`，不新增第二份 SSRF 规则。诊断只记
  host 与字节数，不记 URL 与正文。
- **`render=true` 会执行页面自己的脚本。** 这是"像浏览器一样加载"的固有代价：
  App 提供不注入 JS bridge、不注入 cookie/登录态、不开放文件访问、不持久化
  storage 的一次性 WebView，用后销毁；页面仍可能发自己的追踪请求，设置文案、工具
  描述和授权对话框都说明这一点。渲染仍只把**可见文本**交给模型，不回 raw HTML；
  每回合渲染次数上限（默认 3）是成本闸门。
- **为什么不是"装个代理"或"接个 SearXNG"。** App 内代理是另一类网络配置（哪些
  客户端走代理、代理凭据进 secret store、要绕过 LAN/Tailscale/更新地址），用户已
  确认用系统 VPN，本轮不做；SearXNG/公共实例是"另一个服务"，不是"不依赖提供商"。
- **被否决的替代方案**：让模型改写抓取逻辑或持久化站点适配器。那是"工具改工具"、
  提示注入的落点，也无法用 fixture 钉住；只做了声明式的 `render` 开关，抓取实现
  始终在 App 里。详见 `docs/proposals/local-web-tools.md` §9。
- **它不改变模型层的可见范围。** 抓回的正文照常进入请求并发给对话模型；如果模型
  在境内，正文仍经过它。检索侧"未过滤"不等于回答侧不受约束，产品文档分开描述。

### 1.3 移动端的定位决定"轻"

DSH 是桌面 CLI：多宿主任意挂载、插件图可热重载、会话是文件、可以开一堆子代理。
Android 是：单 app 单进程、随时被系统杀掉、内存以百 MB 计、电量是要省的东西。

**"轻"不是妥协，是需求。** 凡是"桌面需要而手机不需要"的东西都不移植——
Cordis 插件宿主、多宿主 profile、Web UI 都在此列。

### 1.4 付费能力必须显眼，不能写在说明里

有的工具不改变文件，但会让用户在**第三方服务账户上花钱**：`web_search` 和
`web_fetch` 按调用计费。Search 和 Fetch 可以分别选 DeepSeek 或 Exa，各自有独立
key；chat provider 的 key 不授权这两个工具。这类能力有一条独立于审批的规则：

> **用户在选它的地方、和它被使用的地方，都必须看见"要花钱"。**

理由不是"用户会误点"，而是**深埋在描述里的价格等于没有披露**。人扫工具列表时
只看名字；一个放在最右列、和 `writes` 同字号的小写 `paid`，事实上不会被读到。
这不是审美问题，是这条原则要防的失败。

具体到现在的实现，规则是可执行的：

- `ToolCatalog.Entry.paid` 是唯一的事实来源；新增付费工具必须设为 `true`。
  `ToolCatalogTest` 断言付费集合，漏标会让测试红。
- `PAID` 徽标**紧挨工具名**、实心底色、大写；计费说明在工具列表**上方**，
  不是下方。共用组件是 `app/src/main/kotlin/com/inhuman/ui/common/PaidBadge.kt`，
  助手编辑器和设置页都用它，措辞不会两边漂移。
- 对话里的工具结果行也带 `PAID` 徽标——那是费用实际发生的位置，不只是配置界面。
- **披露不是审批。** 默认仍然不问（见 [09-approvals.md](09-approvals.md)）；
  要不要先问由审批规则单独决定。把"付费"默认做成弹窗会破坏"默认不打断"，
  也会训练用户无脑点过。
- 价格变化时改 `PaidToolsNotice` 的文案。现在 backend 可以是 DeepSeek 或
  Exa，价格各不相同且会变；文案明确说“由所选服务按调用计费”，Settings 里显示
  当前 backend 和是否配置 key。**不要**为了“更具体”重新硬编码某一个服务的价格，
  那会对另一部分用户变成错误信息。

这条原则对**以后所有调用第三方付费服务的工具**生效，不只是这两个。

### 1.5 远程能力必须显眼，且不能混进本地工具

SSH 工具不花钱，但它们能造成比花钱更重的后果。规则和付费披露同构：

- `ToolCatalog.Entry.remote = true`，`REMOTE` 徽标紧挨工具名；助手工具列表上方
  有常驻说明，明确说地址簿里没有凭据、远端损坏不可逆、第一次调用要授权。
  `ssh_hosts` 是例外的一半：它在同一开关下、同样要显式选中，但 `remote = false`，
  因为它只列出用户勾选的名字，不连接，也不触发连接授权。
- **"哪些功能没给你用"可以查，但只能查用户能改的那些。** `unavailable_tools`
  以 `ToolCatalog.visible(...)` 为全集：开关关掉的能力（SSH、沙箱、follow-up）
  不在全集里，因此永远不会被这个工具说出名字。否则它就是 §1.2.1 拒绝的那种
  "灰掉但仍宣传"的行，只是变成了文字，而且提示注入正好想知道这些名字。
- **能否 rewind 也是工具标签，不是说明文字。** 所有会改变状态的工具在名字旁带
  `REWIND`（本地可恢复）或 `NO REWIND`（不可恢复），和 `PAID`/`REMOTE` 同一行；
  `ssh_exec` 和 `ssh_upload` 同时有 `REMOTE` 和 `NO REWIND`；`ssh_download` 是
  `REMOTE` + `REWIND`，因为落盘的是工作区副本。设置页审批行、审批弹窗和对话里的
  工具调用行复用同一徽标。理由同 §1.4：用户扫名字时不会展开描述。
- 设置页的 SSH 开关文案说明"打开只是让助手可以选它，不等于授权任何调用"。
- 会话第一次调用弹专用授权对话框，不是普通 `PendingApproval`。它显示
  host/user/第一个操作（命令，或传输的两端路径），要求勾选"可能造成不可逆损坏"，
  才允许。
- 工具结果行、审批对话框**不得显示密码或私钥**。SSH 的普通审批（用户把策略设成
  Ask 时）使用单独的、脱敏的 details；SSH 的 tool-call 行只显示 host 和操作。
- 诊断日志只记 host、端口、用户、命令长度、退出码、耗时；不记命令内容，
  不记密码、私钥、passphrase。

这不是审批：它不改变"默认 Free"的模型，也不把 SSH 默认打开。它是能力披露，
和 §1.4 一样，新增任何远程执行/外传能力都要先过这一节。

### 1.8 内容可以代写，行为不能代写

用户不会写系统提示词，也不会配角色卡、世界书、场景。今天拿到一份能用的配置要经过：
agent 写一版 → 用户复制 → 用户进编辑器粘贴保存 → 用户开一段对话 → 发现不对 →
截图或粘贴回来 → 再改。每一步都要人参与，而且反馈是**残缺**的：system 里真正发出去
的内容、世界书命中了哪几条、模型是在第几轮崩的，都不在截图里。**agent 在改一个它看
不见结果的东西。**

所以答案不是"给用户一个更好的编辑器"，而是：

> **agent 代写用户可配置的内容，用草稿自己试跑、自己改，最后递上一份已经跑过的提案。
> 用户只在三处出现：提供它拿不到的信息、授权一次预算、最后点保存。**

三档边界，判据是"改它会不会改变能力或行为"，而不是"这项有没有 UI"：

| 档 | 内容 | agent 能做什么 |
| --- | --- | --- |
| **A. 可代写** | 系统提示词、角色卡/场景/世界书文本、提示词库条目、工作区根 `AGENTS.md`、名称/标题/描述这类纯文本 | 读、起草、试跑、提案；**写入仍是用户点保存** |
| **B. 只可建议** | 工具选择、服务商/模型、采样参数、审批规则 | 可以说"建议开/关哪个"；提案里**不带这些字段**，用户在原来的编辑器里自己改 |
| **C. 不可碰** | 工具如何运行、沙箱、权限模型、SSH/下载/抓取授权、密钥与 OAuth、全局设置、服务器地址、数据库与代码 | 不写、不提案、不把它解释成可改 |

这条线不是新画的：它和 §1.2 的"工作区类型不是权限层级"是同一件事——**内容不是能力**。
角色卡、场景和 `AGENTS.md` 已经证明"只进 system 的文字不会加工具、审批、授权或网络
路径"，因此代写它们不需要新的"一句话例外"，也不需要新的模式或档位。反过来，任何让
agent 改**行为**的提议都落在 §1.1 排除的那类东西上：它要的不是一段文本，而是一个
可以被说服去打开的权限。

原则成立靠五件事，缺一件就退化成"帮忙生成文本"：

1. **第一手反馈，没有人肉中转。** 试跑必须把转录、实际渲染的 system 摘要、命中的
   世界书条目和失败点直接交回 agent 的上下文。经用户复制、截图、粘贴回来的反馈恰好
   丢掉了这些，而 agent 只能根据看得见的东西改。
2. **试跑不是新的能力层。** 它是一次有界、临时、零能力的模拟：草稿不落库；被试主体
   和模拟用户默认没有工具、文件、网络；要测"会不会正确调用工具"时用 **stub**（预设
   输入/输出），绝不接真实工具；结果只是文本，回到 agent 上下文。所以 §1.1 的"运行期
   不能提升能力"没有被打开——试跑**不授予任何东西**，也不留下一个可复用的权限。
3. **预算是用户的一次授权。** 用户为一次创作会话给出请求数上限，agent 在额度内自己
   迭代；结果里显示剩余，用完即停，不许后台偷跑。额外请求属于 §1.4 的花费披露，
   不因为是"测试"就静默发生。
4. **保存永远是用户的手。** 提案卡是唯一写入口；不自动应用、不静默改配置、不把
   "agent 觉得更好"当成写权限。这与工坊现有的提案体系一致：提案不带工具、服务商、
   模型和审批字段。
5. **模拟不是证据。** 自评只能发现明显失败——跑题、越界、格式坏、泄露设定、该问不问；
   它证明不了"好"。结果卡只能写"这 N 个用例没有失败"，并标明这是模拟、不是真实使用
   的证明；不能把"没失败"说成"好"，也不能把一次试跑结论长期缓存成保证。

**它没有放松任何既有规则。** 代写内容不新增工具类别、不新增授权、不改变
`ToolCatalog` 的形状；试跑不联网、不读写工作区之外、不执行代码；多演员试跑仍遵守
Q4 的上限（一个回合、串行、不递归，见 §3.4），演员不是 subagent。B 档的划线（工具
选择、服务商/模型、采样参数、审批规则）已于 2026-11-27 经用户确认；C 档没有"以后
再说"。

机制未实现（2026-11-27）。主需求、三档与 `trial_run` 的形状记录在
`docs/proposals/authoring-rehearsal.md`；多演员底座（导演/演员/转录、世界书命中、
成本闸门）在 `docs/proposals/cast-run.md`。

## 2. 理念落到设计上的三个后果

### 2.1 文件系统隔离与**代码执行**隔离是两件独立的事

这是这一轮才看清的一点，也是最容易被混为一谈的一点：

| | 现状 | 目标 |
| --- | --- | --- |
| **文件工具**（`read_file` 等） | 走 `SessionWorkspace`，接口级围栏 | **保留**，已通过对抗性审查 |
| **代码执行**（模型写的代码） | `run_javascript`：平台 V8 隔离进程，无网络/文件/模块 API，16 MiB 堆、10 秒上限；设备探测失败则不提供 | 用官方沙箱，但**它拿不到会话目录** |

一个被隔离的进程读不到 app 私有目录里的会话文件夹——这不是配置问题，
是 UID 与 SELinux 域的问题。所以两者是**两道独立的墙**，不需要互相依赖。

**后果：不要试图把工作区挂进沙箱。** 现有的 `_research/android-sandbox/` 里
设计了"虚拟文件系统 + 网络代理"，那是为了**让沙箱能读写文件**。理念反过来：
**沙箱不该有文件系统**，数据由宿主传入、结果由宿主取出。少设计一整套东西。

### 2.2 沙箱里没有网络，所以"执行代码"不等于"能外传"

`fetch` 是 `undefined`。这意味着即使模型写的代码是恶意的，它也**没有出口**——
它只能算出结果交给宿主。宿主再决定这个结果去不去网络（而宿主做这件事时，
走的是我们自己的 `web_search`/`web_fetch`，有预算、有审计）。

**这一条让"允许执行代码"的风险级别下降了一个数量级。**

### 2.3 现有 app 的"每对话一个文件夹"是特性，不是包袱

用户能打开文件、导入、导出、用系统 Files app 浏览——这是它和多数聊天 app 的区别。
**不能因为移植而丢掉。** 但它和"沙箱不碰文件"并不冲突，见 [未决问题 Q2](#q2)。

## 3. 决策记录

七个问题已经答完。**答案优先于本文档其余部分的措辞**——下面第 4 节保留的是当时的
推理过程，不是结论。

### 3.1 边界是结构性的，性能是可调的——这不是矛盾

**Q4 要求给用户调整并发量的权限**，而 §1.1 说"不提供选项"。两者不冲突，
但需要把界线画清楚，否则这条规则会被"那你为什么允许调 X"耗掉：

> **安全边界不可协商，性能预算可以调。**

理由不是措辞游戏。一个可提升的**权限**层级会被攻击者利用——提示注入不需要用户点错，
只需要说服模型去要。而**并发数**提升不了任何能力：调大它只会让同样的操作更快地
耗尽同样的预算。**任何性能旋钮都不改变那道墙，所以它不构成权限提升面。**

据此，`AGENTS.md` 里那句"No full access mode"应当读作：**不存在任何能改变
可及范围的设置**。存在的是"你能多快把它用完"。

### 3.2 Q1 / Q2 —— 会话目录就是工作区

**答案：能力和范围都保持现状——仅限于会话目录的读写与程序执行。**
用户需要 agent 接触别的文件时，**由用户上传到会话目录**（本质是复制：源文件留在
原处，进目录的是一份拷贝）。因此用户必须对会话目录有**手动读写权限**。

两个直接后果：

- **Q2 不需要新概念。** 我原先提议的 `workspace/` 与 `scratch/` 拆分**作废**——
  只有一个目录，用户和 agent 都在里面。用户的控制手段是上传/导出/浏览，不是
  "把东西放进可见层"。
- **"上传是复制"是安全属性，不是实现细节。** 因为源文件从不动，agent 在会话目录里
  无论做什么都**碰不到用户的原始文件**。这条要和沙箱一起写进能力声明。

### 3.3 Q3 —— 用户点了才继续，并提醒关掉后台清理

进程被杀在工具执行中间时：**不自动续跑，停下来等用户点继续**；
同时在界面上提示用户去手机设置里关闭对该 app 的后台清理，
**用户可以选择不再提示**。

"不自动续跑"的理由不是技术做不到，是**钱和网络**：自动续跑会在用户没看着的时候
继续调用模型和搜索。

### 3.4 Q4 —— 默认小，可调，带风险提示

默认值要**偏小**（并行工具调用与子代理并发），用户可调，调整时**给出性能与
电量风险的说明**。按 §3.1，这是可调项，不是边界项。

### 3.5 Q5 —— 日志给用户看，也给用户导出；agent 不看自己的日志

**用户可见、可导出。agent 不读自己的日志。** 而且——原话值得直接记下来：

> DSH 的日志很详细，我们的**只能更详细，不能偷工减料**。

这条把日志从"内部实现"提升成**产品的一部分**：它是用户能自己核对 agent 做过什么的地方。
与 §1.2 的关系是直接的——**"能力边界能被一句话说清"的下一步，是能被用户自己查证。**

它仍在会话目录之外（`filesDir` 下的 app 数据库区），所以 8 个文件工具够不到它。
这不是限制，是 Q5 的另一半：日志是给**人**看的，不是给 agent 当记忆用的
（那是上下文与压缩的职责）。

### 3.6 Q6 —— 采纳：能力自检，失败即降级

启动时断言边界仍然成立（沙箱里 `fetch` 是 `undefined`、读不到 `filesDir`、
堆上限生效）。**失败不是警告，而是关掉代码执行并告诉用户。**
理由见 §1.1：不依赖配置正确，依赖边界可测。

**已经实现的是工作区围栏这一半。** `WorkspaceSelfCheck` 在
`InhumanApp.onCreate` 里、第一帧之前运行：相对路径、`..`、绝对路径、工作区外
文件、符号链接、Windows 目录联接，六条断言都在缓存里的临时目录完成，探针显式
删除，不递归删除含链接的树。失败（或自检根本跑不起来）时
`AppCapabilities.workspaceOk = false`：文件、媒体与 SSH 等依赖工作区的工具从
请求和选择器里消失，聊天页显示失败断言；Files 仍然打开用户自己的文件。下一次
启动重新问。

代码执行的那三条断言（`fetch` 未定义、读不到 `filesDir`、堆上限）由
`SandboxRuntime.probe()` 在提供 `run_javascript` 的进程里做，不在
`WorkspaceSelfCheck` 里：JavaScript 隔离进程没有工作区可检查。探测逐项检查
`fetch`/`XMLHttpRequest`/`WebSocket`/`require`/`process` 是 `undefined`、
`1+1` 返回 `"2"`，并给 isolate 设置堆上限；任何一项失败，工具就从请求和
选择器里移除，原因写进 Diagnostics。**失败不是警告。**

### 3.7 Q7 —— 开源

**决定：开源。**

但要把两个事实分开，因为它们的结论相反：

1. **开源不是为了能抄 DSH。** DSH 是 MIT，抄它**今天就是合法的**——它自带的
   287 个包全是 MIT / MPL-2.0 / BSD-3-Clause，无 GPL。
2. **开源也不是引入 JLaTeXMath 的前提。** 见第 4 节 Q7——它带链接例外，
   闭源链接本来就可以。**README 里"为了避开 GPL 而放弃 LaTeX"这句话在许可上
   过于保守**，应当更正。

**那开源的理由是什么？** 是 §1.2 的延伸：这个 app 的核心主张是"围栏是真的"，
而**一个自称安全却不可审计的实现，说服力有限**。开源让它可被检验。

具体后果（待定）：

- **许可证选择。** Apache-2.0 与 Android 生态一致，且与现有依赖相容。
- **依赖重新评估。** 那些"为了避 GPL 而放弃"的东西值得重新看一眼——但要看的是
  **真实代价**（捆绑字体、`THIRD-PARTY-NOTICES` 的维护），不是许可证恐惧。
- **`THIRD-PARTY-NOTICES` 成为必须维护的文件**，这是开源的实际工作量之一。

## 4. 当时的推理过程（保留，不当作结论）

按"影响架构的程度"排序，不按难度。前三个定了，后面才有意义。

<a id="q1"></a>
### Q1. 权限模式 vs 能力声明——最大的一个

DSH 有 `sandbox/mode`、`permission/preset`、`approval/policy` 三类事件，
都是**模式**：用户选一个档位，行为随之改变。

理念 1.1 排除模式。那替代品是什么？

**方向：能力是助手的静态属性，不是会话的运行期状态。**
现有 `toolsJson`（`ConversationEntity.toolsJson`，空串 = 全部，`[]` = 全不）
已经表达了这个意思，而且 `ToolCatalog.permits()` 已经检查了"选择的**且**存在的"。

需要定的：
- 审批门怎么表达？现在的答案是**用户配置的规则**（见 09），`needsApproval(arguments)`
  只剩下"这个工具永远要问"的钩子，仍按调用求值。这个形状比"模式"好——它是
  **针对具体动作**的问句，不是档位；应当保留，而不是换成一个 `approval/policy`
  式的事件。
- 一个助手**不该**有的能力，是不是应该连**工具名都不出现**在请求里？
  现在是（`buildTools` 过滤），这是对的：模型看不见的能力，注入也拿不到。

<a id="q2"></a>
### Q2. Agent 只能"呈现结果"，用户仍要看到文件——两者怎么并存

理念 2.1 说沙箱不碰文件。那用户熟悉的工作区怎么活？

**我的看法（待你确认）：分成两个概念，而不是一个。**

```
workspace/          用户可见、可导入导出、系统 Files 能浏览 —— 保留现状
  ↑ 只有用户操作和"呈现结果"能写入
scratch/            模型的工作区，工具可读写，用户平时看不见
  ↑ 现有 8 个文件工具继续在这里工作
```

`present`（DSH 有这个工具，我实测到 27 个 `deliverables/presented` 事件）
是**从 scratch 到 workspace 的那一次显式动作**。它天然是一个审批点：
"把 `report.md` 放到你的文件夹里？"

好处：模型仍能读写文件（现有工具一行不改），但**用户可见的那一层只被
显式动作改动**。这比"全都能写"和"全都不能写"都好。

代价：多一个概念要解释。

<a id="q3"></a>
### Q3. 手机上的"后台被杀"——恢复语义

这是桌面不存在的约束。Android 会在任意时刻杀掉进程，OEM 更激进。
DSH 的模型能优雅处理（日志即真相），但**行为**要定：

- 被杀在工具执行中间，重开时**自动续跑**还是**停在那里等用户点继续**？
  我倾向后者：自动续跑会在用户没看着的时候花钱、发网络请求。
- 一次 turn 里最多 8 轮工具，每轮可能一次网络请求——**用户锁屏后该不该继续？**
  需要前台服务，还是接受"切后台就暂停"？后者简单且省电，但长搜索会中断。

<a id="q4"></a>
### Q4. 子代理与并发的移动端上限

DSH 有 subagent、workflow（几十个子代理扇出）、并行工具调用（默认 10）。
手机上 10 个并行网络请求 + 10 份上下文，电量与内存都吃紧。

**需要定一个"手机上的上限"**，并且它应当是**硬性**的（理念 1.1），
不是"默认值可调"。我倾向：并行工具调用 2–3，子代理 1（串行），
且子代理不无限递归。

**落地时定成了：工具 1、进程 2、子代理 0。** 工具保持串行，因为审批、
检查点、取消和"一个回合最多几次调用"的记账都依赖一次只跑一个；把"并行"
换成**并发对话回合**——每个进程最多 2 个——才是手机上真正有用、且能同时被
通知栏表示的量。子代理没有实现，所以上限是 0；将来若加，仍是 1 个、串行、
不递归。实现和测试见 `docs/06-agent-loop-ui.md` 的 "Concurrency ceilings"、
`TurnConcurrency` 与 `ChatEngineTest` 的重叠计数测试。

<a id="q5"></a>
### Q5. 会话日志与"用户可见的文件"的关系

移植后日志是 JSONL/事件表。要不要让用户能打开、导出、看见？DSH 的是文件且可读。

**看法**：导出**可以**，但要说清楚里面有什么——它包含完整对话、工具参数、
搜索结果。默认**不**暴露在 Files app 里，除非用户主动导出。
理由：这和我们不让沙箱碰它是同一个理由——**它不是给文件浏览器的东西，是 app 的数据库。**

<a id="q6"></a>
### Q6. 能力清单要不要"可证明"

理念 1.2 要求一句话说清能力。能不能做得更硬——**把这句话变成可验证的**？

比如一个自检：启动时断言"沙箱里 `fetch` 是 `undefined`"、"沙箱读不到
`filesDir`"。失败就不是"警告"，而是**关掉代码执行并告诉用户**。

这和 1.1 是同一个思路：**不依赖配置正确，依赖边界可测。**
成本不高（`JavaScriptSandboxProbe` 已经证明了每条都能在设备上问出来），
但它把"我们说安全"变成"设备说安全"。**已落地：`SandboxRuntime.probe()` 在
提供 `run_javascript` 前做这三项断言，失败就移除工具。**

<a id="q7"></a>
### Q7. 开源，以及开源带来什么约束

> **已决定开源。见 §3.7。** 以下为当时的推理，保留以便追溯，但其中"引入 JLaTeXMath
> 以开源为前提"这一条**是错的**——该库带链接例外，闭源链接本来就可以。

你提到"如果闭源导致困难就开源"。这件事有**具体的技术后果**，不只是授权：

- 现状里**为了避开 GPL 已经做了取舍**：README 明确写了不渲染 LaTeX，
  因为唯一可行的 Android 方案 JLaTeXMath 是 GPLv2。**开源会让这个取舍消失**。
- DSH 是 MIT，抄代码**现在就是合法的**（我查过它自带的 287 个包：MIT/MPL-2.0/BSD-3-Clause，
  无 GPL）。所以开源**不是**为了能抄 DSH——那件事没有法律障碍。
- 开源真正的收益是别的：**别人能审沙箱**。这个 app 的核心主张是"围栏是真的"，
  而一个主张自己安全却不可审计的实现，说服力有限。

**需要你定的**：开源是手段（为了让某件事更容易），还是目标（本来就想开源）？
这影响依赖选择——如果开源，JLaTeXMath 之类的 GPL 方案就重新可用，
而 README 里那些"为了避 GPL 而放弃的功能"需要重新评估。
