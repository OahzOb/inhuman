# 08 — 移植理念与未决问题

这不是对现状的描述，是**约束**。它决定后面所有设计取舍，也决定哪些东西
**不做**——包括那些"加上去也无妨"的选项。

---

## 1. 理念

**DeepSeek Harness 的 agent 设计是好的，我们要把它搬到 Android 上。**
但用户群体的需求、系统本身的封闭性、以及移动端设备的定位，决定了必须加一层
**硬性限制**：限制读写、限制程序执行。

限制的**目的不是免责**。是：

> **借用设备的性能资源，同时隔离文件系统。**
> **不以脱责为目的，要追求用户体验和安全性。**

三条推论，每一条都排除了一类做法；另有一条关于花钱的规则：

### 1.1 不提供 "full access" 这类选项

不是"默认安全、高级用户可解锁"，而是**根本不设这个开关**。

理由不是"用户会选错"，而是更硬的：**一个可提升的权限层级，本身就是一个攻击面。**
提示注入不需要用户点错，它只需要**说服模型去要**更高的权限。而"要权限"这件事，
在 DSH 的模型里是**一等公民**——它有 `permission/preset`、`sandbox/mode`、
`approval/policy` 三类持久事件，就是权限模式切换留下的记录。

对照实测：DSH 自己的沙箱会**降级**。它的文档写着，沙箱启动失败时默认**不加沙箱运行**，
除非显式配置。那条"逃生舱"就是本节要排除的东西。

**所以：能力在对话创建时确定，运行期不能提升。** 没有"要更多权限"的路径，
因为不存在更多权限可以给。

### 1.2 能力边界要能被一句话说清

现有实现有一个对的方向：`requiresOptIn` 那类标注迫使调用方显式承认能力，
而**助手（assistant）本来就带一个工具清单**（`toolsJson`）。
这说明"能力是助手的属性"这个想法已经有了实现基础。

用户要能读到的话不是"ask / never / full access"，而是：

> **代码在你的设备上运行，只看到你给它的东西，连不出网，也碰不到你的文件。**

这句话必须是**真的**，而且**不因设置而变**。实测支持它：官方沙箱里
`fetch`、`require`、`process` 全是 `undefined`——**网络是平台切断的，不是我们加的墙。**

有一条例外不在 agent 的能力里，而在用户的操作里：Files 的 **Download from a
URL**。URL 由用户输入，文件落到工作区或用户通过 SAF 选择的目录；app 不因此获得
通用存储权限，**工具目录里没有这个能力，agent 也调不到它**。它打开的是用户的手，
不是模型的路。除此之外，能离开设备的仍然只有 SSH 工具和用户主动选择的付费 web 工具。

### 1.2.1 唯一被批准的例外：SSH，默认关闭，按会话确认

SSH 工具（`ssh_exec`、`ssh_upload`、`ssh_download`）打破上面那句话的两个部分：
agent 可以连网，也可以在**另一台机器**上执行任意命令、读写文件。这是用户明确
要求的能力，不能靠"文档里不写"解决。约束是：

- **默认关闭，且是两层关闭**：Settings 的全局开关默认关；即使打开，助手还必须在
  工具清单里显式选中要用的每一个 SSH 工具；第一次调用时，会话里再弹一次**能力
  授权**，不是普通的单次审批。`toolsJson = null` 的历史助手**不会**自动获得 SSH——
  `ToolCatalog.permits` 对所有 `remote = true` 的工具特判，必须显式写进清单。
- **app 不提供远程设备配置**：没有 host 列表、没有凭据仓库、没有 allowlist。
  连接信息由用户告诉 agent；app 只做传输。这是刻意的：一个 host 列表会把
  "用户临时给一台机器"变成"app 管理一支舰队"。工具调用参数在写入 transcript
  之前会去掉 `password`/`privateKey`/`passphrase`；用户自己打进消息的文本仍会
  被保存，这是会话本身。
- **授权按会话持久化**，可撤销；全局开关关闭会清掉所有会话的授权。
  授权后，后续调用回到普通 `ToolPolicy`（默认 Free），不再逐条询问。
- **会话工具集只由用户改，且从下一回合生效**。对话菜单里可以增删这个会话
  使用的工具；模型不能调用任何东西来改它，消息和工具结果也不能。候选范围是
  助手已有的工具加上这个会话已经有的工具，对话不能凭空获得助手从未提供的
  能力。放宽是用户勾选并点“应用”这一下，不是新的逐次审批；SSH 工具仍须显式
  选中，并按 §1.5 走会话授权。编辑后保存的是显式清单，以后的版本新增工具不会
  自动进来。
- **传输安全仍在**：host key TOFU，标准 `SHA256:` 指纹，变 key 失败关闭；
  可显式给指纹。这不是权限限制，是防中间人。
- **风险在远端，不在工作区副本**：命令可以删数据、停服务、改权限，上传可以覆盖
  远端文件，且都不可撤销；下载把远端内容带进工作区，占配额，也可能带来提示注入。
  授权文案必须说清这一点，也必须说清粘贴的密码/私钥会进入会话并发给 DeepSeek；
  工作区里的 key 文件只在本地读取，但工作区文件可以被带到远端。

这不是"full access"模式：没有本地权限提升，没有可累积的权限层级，没有
"高级用户解锁"。它是一个**用户显式打开、按会话授权、可撤销的远程命令与文件
传输通道**。但它确实是对 §1.2 那句话的例外；当 SSH 关闭时（默认），原句仍然成立。
文档不再声称"任何设置下都连不出网"——只在 SSH 关闭时成立。

### 1.3 移动端的定位决定"轻"

DSH 是桌面 CLI：多宿主任意挂载、插件图可热重载、会话是文件、可以开一堆子代理。
Android 是：单 app 单进程、随时被系统杀掉、内存以百 MB 计、电量是要省的东西。

**"轻"不是妥协，是需求。** 凡是"桌面需要而手机不需要"的东西都不移植——
Cordis 插件宿主、多宿主 profile、Web UI 都在此列。

### 1.4 付费能力必须显眼，不能写在说明里

有的工具不改变文件，但会让用户在**第三方服务账户上花钱**：`web_search` 和
`web_fetch` 按调用计费。Search 和 Fetch 可以分别选 DeepSeek 或 Exa，各自有独立
key；chat provider 的 key 不授权这两个工具。这类能力有一条独立于审批的规则：

> **用户在选它的地方、和它被使用的地方，都必须看见"要花钱"。**

理由不是"用户会误点"，而是**深埋在描述里的价格等于没有披露**。人扫工具列表时
只看名字；一个放在最右列、和 `writes` 同字号的小写 `paid`，事实上不会被读到。
这不是审美问题，是这条原则要防的失败。

具体到现在的实现，规则是可执行的：

- `ToolCatalog.Entry.paid` 是唯一的事实来源；新增付费工具必须设为 `true`。
  `ToolCatalogTest` 断言付费集合，漏标会让测试红。
- `PAID` 徽标**紧挨工具名**、实心底色、大写；计费说明在工具列表**上方**，
  不是下方。共用组件是 `app/src/main/kotlin/com/inhuman/ui/common/PaidBadge.kt`，
  助手编辑器和设置页都用它，措辞不会两边漂移。
- 对话里的工具结果行也带 `PAID` 徽标——那是费用实际发生的位置，不只是配置界面。
- **披露不是审批。** 默认仍然不问（见 [09-approvals.md](09-approvals.md)）；
  要不要先问由审批规则单独决定。把"付费"默认做成弹窗会破坏"默认不打断"，
  也会训练用户无脑点过。
- 价格变化时改 `PaidToolsNotice` 的文案。现在 backend 可以是 DeepSeek 或
  Exa，价格各不相同且会变；文案明确说“由所选服务按调用计费”，Settings 里显示
  当前 backend 和是否配置 key。**不要**为了“更具体”重新硬编码某一个服务的价格，
  那会对另一部分用户变成错误信息。

这条原则对**以后所有调用第三方付费服务的工具**生效，不只是这两个。

### 1.5 远程能力必须显眼，且不能混进本地工具

SSH 工具不花钱，但它们能造成比花钱更重的后果。规则和付费披露同构：

- `ToolCatalog.Entry.remote = true`，`REMOTE` 徽标紧挨工具名；助手工具列表上方
  有常驻说明，明确说 app 不配置 host、远端损坏不可逆、第一次调用要授权。
- **能否 rewind 也是工具标签，不是说明文字。** 所有会改变状态的工具在名字旁带
  `REWIND`（本地可恢复）或 `NO REWIND`（不可恢复），和 `PAID`/`REMOTE` 同一行；
  `ssh_exec` 和 `ssh_upload` 同时有 `REMOTE` 和 `NO REWIND`；`ssh_download` 是
  `REMOTE` + `REWIND`，因为落盘的是工作区副本。设置页审批行、审批弹窗和对话里的
  工具调用行复用同一徽标。理由同 §1.4：用户扫名字时不会展开描述。
- 设置页的 SSH 开关文案说明"打开只是让助手可以选它，不等于授权任何调用"。
- 会话第一次调用弹专用授权对话框，不是普通 `PendingApproval`。它显示
  host/user/第一个操作（命令，或传输的两端路径），要求勾选"可能造成不可逆损坏"，
  才允许。
- 工具结果行、审批对话框**不得显示密码或私钥**。SSH 的普通审批（用户把策略设成
  Ask 时）使用单独的、脱敏的 details；SSH 的 tool-call 行只显示 host 和操作。
- 诊断日志只记 host、端口、用户、命令长度、退出码、耗时；不记命令内容，
  不记密码、私钥、passphrase。

这不是审批：它不改变"默认 Free"的模型，也不把 SSH 默认打开。它是能力披露，
和 §1.4 一样，新增任何远程执行/外传能力都要先过这一节。

## 2. 理念落到设计上的三个后果

### 2.1 文件系统隔离与**代码执行**隔离是两件独立的事

这是这一轮才看清的一点，也是最容易被混为一谈的一点：

| | 现状 | 目标 |
| --- | --- | --- |
| **文件工具**（`read_file` 等） | 走 `SessionWorkspace`，接口级围栏 | **保留**，已通过对抗性审查 |
| **代码执行**（模型写的代码） | 不存在 | 用官方沙箱，但**它拿不到会话目录** |

一个被隔离的进程读不到 app 私有目录里的会话文件夹——这不是配置问题，
是 UID 与 SELinux 域的问题。所以两者是**两道独立的墙**，不需要互相依赖。

**后果：不要试图把工作区挂进沙箱。** 现有的 `_research/android-sandbox/` 里
设计了"虚拟文件系统 + 网络代理"，那是为了**让沙箱能读写文件**。理念反过来：
**沙箱不该有文件系统**，数据由宿主传入、结果由宿主取出。少设计一整套东西。

### 2.2 沙箱里没有网络，所以"执行代码"不等于"能外传"

`fetch` 是 `undefined`。这意味着即使模型写的代码是恶意的，它也**没有出口**——
它只能算出结果交给宿主。宿主再决定这个结果去不去网络（而宿主做这件事时，
走的是我们自己的 `web_search`/`web_fetch`，有预算、有审计）。

**这一条让"允许执行代码"的风险级别下降了一个数量级。**

### 2.3 现有 app 的"每对话一个文件夹"是特性，不是包袱

用户能打开文件、导入、导出、用系统 Files app 浏览——这是它和多数聊天 app 的区别。
**不能因为移植而丢掉。** 但它和"沙箱不碰文件"并不冲突，见 [未决问题 Q2](#q2)。

## 3. 决策记录

七个问题已经答完。**答案优先于本文档其余部分的措辞**——下面第 4 节保留的是当时的
推理过程，不是结论。

### 3.1 边界是结构性的，性能是可调的——这不是矛盾

**Q4 要求给用户调整并发量的权限**，而 §1.1 说"不提供选项"。两者不冲突，
但需要把界线画清楚，否则这条规则会被"那你为什么允许调 X"耗掉：

> **安全边界不可协商，性能预算可以调。**

理由不是措辞游戏。一个可提升的**权限**层级会被攻击者利用——提示注入不需要用户点错，
只需要说服模型去要。而**并发数**提升不了任何能力：调大它只会让同样的操作更快地
耗尽同样的预算。**任何性能旋钮都不改变那道墙，所以它不构成权限提升面。**

据此，`AGENTS.md` 里那句"No full access mode"应当读作：**不存在任何能改变
可及范围的设置**。存在的是"你能多快把它用完"。

### 3.2 Q1 / Q2 —— 会话目录就是工作区

**答案：能力和范围都保持现状——仅限于会话目录的读写与程序执行。**
用户需要 agent 接触别的文件时，**由用户上传到会话目录**（本质是复制：源文件留在
原处，进目录的是一份拷贝）。因此用户必须对会话目录有**手动读写权限**。

两个直接后果：

- **Q2 不需要新概念。** 我原先提议的 `workspace/` 与 `scratch/` 拆分**作废**——
  只有一个目录，用户和 agent 都在里面。用户的控制手段是上传/导出/浏览，不是
  "把东西放进可见层"。
- **"上传是复制"是安全属性，不是实现细节。** 因为源文件从不动，agent 在会话目录里
  无论做什么都**碰不到用户的原始文件**。这条要和沙箱一起写进能力声明。

### 3.3 Q3 —— 用户点了才继续，并提醒关掉后台清理

进程被杀在工具执行中间时：**不自动续跑，停下来等用户点继续**；
同时在界面上提示用户去手机设置里关闭对该 app 的后台清理，
**用户可以选择不再提示**。

"不自动续跑"的理由不是技术做不到，是**钱和网络**：自动续跑会在用户没看着的时候
继续调用模型和搜索。

### 3.4 Q4 —— 默认小，可调，带风险提示

默认值要**偏小**（并行工具调用与子代理并发），用户可调，调整时**给出性能与
电量风险的说明**。按 §3.1，这是可调项，不是边界项。

### 3.5 Q5 —— 日志给用户看，也给用户导出；agent 不看自己的日志

**用户可见、可导出。agent 不读自己的日志。** 而且——原话值得直接记下来：

> DSH 的日志很详细，我们的**只能更详细，不能偷工减料**。

这条把日志从"内部实现"提升成**产品的一部分**：它是用户能自己核对 agent 做过什么的地方。
与 §1.2 的关系是直接的——**"能力边界能被一句话说清"的下一步，是能被用户自己查证。**

它仍在会话目录之外（`filesDir` 下的 app 数据库区），所以 8 个文件工具够不到它。
这不是限制，是 Q5 的另一半：日志是给**人**看的，不是给 agent 当记忆用的
（那是上下文与压缩的职责）。

### 3.6 Q6 —— 采纳：能力自检，失败即降级

启动时断言边界仍然成立（沙箱里 `fetch` 是 `undefined`、读不到 `filesDir`、
堆上限生效）。**失败不是警告，而是关掉代码执行并告诉用户。**
理由见 §1.1：不依赖配置正确，依赖边界可测。

### 3.7 Q7 —— 开源

**决定：开源。**

但要把两个事实分开，因为它们的结论相反：

1. **开源不是为了能抄 DSH。** DSH 是 MIT，抄它**今天就是合法的**——它自带的
   287 个包全是 MIT / MPL-2.0 / BSD-3-Clause，无 GPL。
2. **开源也不是引入 JLaTeXMath 的前提。** 见第 4 节 Q7——它带链接例外，
   闭源链接本来就可以。**README 里"为了避开 GPL 而放弃 LaTeX"这句话在许可上
   过于保守**，应当更正。

**那开源的理由是什么？** 是 §1.2 的延伸：这个 app 的核心主张是"围栏是真的"，
而**一个自称安全却不可审计的实现，说服力有限**。开源让它可被检验。

具体后果（待定）：

- **许可证选择。** Apache-2.0 与 Android 生态一致，且与现有依赖相容。
- **依赖重新评估。** 那些"为了避 GPL 而放弃"的东西值得重新看一眼——但要看的是
  **真实代价**（捆绑字体、`THIRD-PARTY-NOTICES` 的维护），不是许可证恐惧。
- **`THIRD-PARTY-NOTICES` 成为必须维护的文件**，这是开源的实际工作量之一。

## 4. 当时的推理过程（保留，不当作结论）

按"影响架构的程度"排序，不按难度。前三个定了，后面才有意义。

<a id="q1"></a>
### Q1. 权限模式 vs 能力声明——最大的一个

DSH 有 `sandbox/mode`、`permission/preset`、`approval/policy` 三类事件，
都是**模式**：用户选一个档位，行为随之改变。

理念 1.1 排除模式。那替代品是什么？

**方向：能力是助手的静态属性，不是会话的运行期状态。**
现有 `toolsJson`（`ConversationEntity.toolsJson`，空串 = 全部，`[]` = 全不）
已经表达了这个意思，而且 `ToolCatalog.permits()` 已经检查了"选择的**且**存在的"。

需要定的：
- 审批门怎么表达？现在的答案是**用户配置的规则**（见 09），`needsApproval(arguments)`
  只剩下"这个工具永远要问"的钩子，仍按调用求值。这个形状比"模式"好——它是
  **针对具体动作**的问句，不是档位；应当保留，而不是换成一个 `approval/policy`
  式的事件。
- 一个助手**不该**有的能力，是不是应该连**工具名都不出现**在请求里？
  现在是（`buildTools` 过滤），这是对的：模型看不见的能力，注入也拿不到。

<a id="q2"></a>
### Q2. Agent 只能"呈现结果"，用户仍要看到文件——两者怎么并存

理念 2.1 说沙箱不碰文件。那用户熟悉的工作区怎么活？

**我的看法（待你确认）：分成两个概念，而不是一个。**

```
workspace/          用户可见、可导入导出、系统 Files 能浏览 —— 保留现状
  ↑ 只有用户操作和"呈现结果"能写入
scratch/            模型的工作区，工具可读写，用户平时看不见
  ↑ 现有 8 个文件工具继续在这里工作
```

`present`（DSH 有这个工具，我实测到 27 个 `deliverables/presented` 事件）
是**从 scratch 到 workspace 的那一次显式动作**。它天然是一个审批点：
"把 `report.md` 放到你的文件夹里？"

好处：模型仍能读写文件（现有工具一行不改），但**用户可见的那一层只被
显式动作改动**。这比"全都能写"和"全都不能写"都好。

代价：多一个概念要解释。

<a id="q3"></a>
### Q3. 手机上的"后台被杀"——恢复语义

这是桌面不存在的约束。Android 会在任意时刻杀掉进程，OEM 更激进。
DSH 的模型能优雅处理（日志即真相），但**行为**要定：

- 被杀在工具执行中间，重开时**自动续跑**还是**停在那里等用户点继续**？
  我倾向后者：自动续跑会在用户没看着的时候花钱、发网络请求。
- 一次 turn 里最多 8 轮工具，每轮可能一次网络请求——**用户锁屏后该不该继续？**
  需要前台服务，还是接受"切后台就暂停"？后者简单且省电，但长搜索会中断。

<a id="q4"></a>
### Q4. 子代理与并发的移动端上限

DSH 有 subagent、workflow（几十个子代理扇出）、并行工具调用（默认 10）。
手机上 10 个并行网络请求 + 10 份上下文，电量与内存都吃紧。

**需要定一个"手机上的上限"**，并且它应当是**硬性**的（理念 1.1），
不是"默认值可调"。我倾向：并行工具调用 2–3，子代理 1（串行），
且子代理不无限递归。

<a id="q5"></a>
### Q5. 会话日志与"用户可见的文件"的关系

移植后日志是 JSONL/事件表。要不要让用户能打开、导出、看见？DSH 的是文件且可读。

**看法**：导出**可以**，但要说清楚里面有什么——它包含完整对话、工具参数、
搜索结果。默认**不**暴露在 Files app 里，除非用户主动导出。
理由：这和我们不让沙箱碰它是同一个理由——**它不是给文件浏览器的东西，是 app 的数据库。**

<a id="q6"></a>
### Q6. 能力清单要不要"可证明"

理念 1.2 要求一句话说清能力。能不能做得更硬——**把这句话变成可验证的**？

比如一个自检：启动时断言"沙箱里 `fetch` 是 `undefined`"、"沙箱读不到
`filesDir`"。失败就不是"警告"，而是**关掉代码执行并告诉用户**。

这和 1.1 是同一个思路：**不依赖配置正确，依赖边界可测。**
成本不高（`JavaScriptSandboxProbe` 已经证明了每条都能在设备上问出来），
但它把"我们说安全"变成"设备说安全"。

<a id="q7"></a>
### Q7. 开源，以及开源带来什么约束

> **已决定开源。见 §3.7。** 以下为当时的推理，保留以便追溯，但其中"引入 JLaTeXMath
> 以开源为前提"这一条**是错的**——该库带链接例外，闭源链接本来就可以。

你提到"如果闭源导致困难就开源"。这件事有**具体的技术后果**，不只是授权：

- 现状里**为了避开 GPL 已经做了取舍**：README 明确写了不渲染 LaTeX，
  因为唯一可行的 Android 方案 JLaTeXMath 是 GPLv2。**开源会让这个取舍消失**。
- DSH 是 MIT，抄代码**现在就是合法的**（我查过它自带的 287 个包：MIT/MPL-2.0/BSD-3-Clause，
  无 GPL）。所以开源**不是**为了能抄 DSH——那件事没有法律障碍。
- 开源真正的收益是别的：**别人能审沙箱**。这个 app 的核心主张是"围栏是真的"，
  而一个主张自己安全却不可审计的实现，说服力有限。

**需要你定的**：开源是手段（为了让某件事更容易），还是目标（本来就想开源）？
这影响依赖选择——如果开源，JLaTeXMath 之类的 GPL 方案就回到桌面上，
而 README 里那些"为了避 GPL 而放弃的功能"需要重新评估。
