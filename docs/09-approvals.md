## 1. 三个问题，三层回答

| 问题 | 回答 | 可配置？ |
| --- | --- | --- |
| 工具能碰到哪些**路径**？ | 会话目录，且仅此 | **不可**（`SessionWorkspace` 保证） |

## 2. 冲突：你要求的两条规则不能同时成立

你说：

- **"删文件"** → 审批
- **"每个文件或目录也都可以配置是否需要审批，甚至只读"** → 用户可配

如果路径可以被配成"自由"，那**用户就能把删除配成无需审批**。而"删文件要审批"
被单独提出来作为第一句要求，说明它不是可选项。

**我的建议：删除是地板，不是默认值。**

> **删除、覆盖、移出受保护路径——这三类不可逆动作永远需要确认，
> 任何配置都不能关掉它。**

理由不是"怕用户配错"，而是：**这个 app 的全部安全主张，依赖于"在共享目录里，
任何不可逆的事都发生在一次明确的确认之后"这句可验证的话。** 一旦它可以被配置关掉，
这句话就变成"通常成立"，而那正是提示注入需要的空间——注入不需要说服用户改设置，
它只需要一次"这次别问了"的疲劳点击。

所以配置的能力是**单向的**：可以更严，不能更松于地板。

**如果你不同意这条，请直接说**——这是本文唯一一处我在你的要求上加了约束。

## 3. 三层策略

### 3.1 全局默认

每个工具一个默认值。按"可逆性"而不是按"危险感"定：

| 工具 | 默认 | 理由 |
| --- | --- | --- |
| `read_file` `list_files` `search_files` `file_info` `read_time` `web_search` `web_fetch` | 不问 | 只读，且改不了任何东西 |
| `write_file`（**新建**） | 不问 | 在会话目录里加东西是可逆的：删掉即可，且删除本身有门 |
| `write_file`（**覆盖已有**） | 问 | 不可逆：旧内容没了 |
| `delete_file` `move_file` | **永远问** | 地板，见 §2 |

这比现在的状态（只有 `delete_file` 问）多一条：**覆盖已有文件要问**。
理由和删除一样，而且共享一个目录之后更明显——**agent 能覆盖用户刚上传的文件**，
而"上传是复制"只保护了源文件，不保护目录里那一份。

### 3.2 agent 自定义

沿用现有结构：助手（agent）本来带一个工具清单（`ConversationEntity.toolsJson`，
空串 = 全部，`[]` = 全不；`ToolCatalog.permits()` 检查"选择的**且**存在的"）。

**agent 层只能收紧，不能放宽。** 一个"研究助手"可以把 `write_file` 设为永远问，
但不能把 `delete_file` 设为不问。这样"换一个 agent"就不是一条提权路径。

### 3.3 路径策略

对会话目录内的**具体文件或目录**设规则，**只对 agent 生效**：

| 取值 | 含义 |
| --- | --- |
| `free` | 按上层策略（**仍受地板约束**） |
| `needs-approval` | 任何写/删都问 |
| `read-only` | agent 只能读；写与删直接**拒绝**（不是"问"） |
| `agent-blind` | agent 看不见它（不出现在 `list_files`，无法 `read_file`） |

`agent-blind` 是新增的一档，用途很明确：用户的私人笔记、密钥文件、未整理的草稿。
它比 `read-only` 更彻底——**看不见比看得见但不能改更安全**，因为文件名本身可能泄密。

**路径规则限制的是 agent，不是用户。** 用户永远能读写自己的会话目录；
把文件设成 `read-only` 是"agent 不许动它"，不是"我也不能动它"。
用户在 app 里仍然可以重命名、删除、导出。

### 3.4 合成规则：取最严

```
effective(tool, path) =
    floor(tool, path)                    ← §2，不可配置
  ⊔ agentOverride(tool)                  ← 只能收紧
  ⊔ pathPolicy(path)                     ← 只能收紧
  ⊔ globalDefault(tool)                  ← 默认值
```

`⊔` 是"取更严的那个"。**没有一层能放松另一层**，所以配置的语义是可预测的：
你无论怎么调，都不会比默认更松于地板。

## 4. 评审的三个具体后果

### 4.1 覆盖已有文件要问，是新增的门

现在的 `DeleteFileTool.needsApproval` 硬编码 `true`（`FileTools.kt:316`），
`WriteFileTool` 不问。按 §3.1，`WriteFileTool` 要变成**看路径是否存在**：
不存在不问，存在则问（且除非路径策略是 `free` 且没有别的收紧）。

实现上这是 `needsApproval(arguments)` 里的一次存在性检查——签名不变。

### 4.2 路径策略要能"拒绝"，不只是"问"

`read-only` 与 `agent-blind` 的语义是**拒绝**，而现在的 `needsApproval` 只有
"问/不问"两态。所以要么：

- 让 `needsApproval` 之外多一个"这个调用被策略禁止"的判定，或
- 在工具 `execute` 里返回 `ToolResult.error(...)`

**我倾向前者**：拒绝应当发生在调用**之前**、由策略层统一决定，而不是让每个工具
自己去查策略——否则八个工具就是八处可能忘记检查的地方。

### 4.3 审批决定应当进会话日志

按 08 的 Q5（日志给用户看、要更详细），每一次"问了、用户答了什么"都应当是
**持久事件**，而不是只活在内存里的 UI 状态。

这也直接修掉 B4：现在用户拒绝一轮里的第一个工具调用时，同一个 round 里
**后面的调用不会被处理**（`ChatViewModel.kt:1128` 直接 return），于是
`toolCallsJson` 里留着没有结果的调用——app 自己的注释说这种 transcript 是
API 会拒绝的请求（`:1282-1292`）。事件化之后，"这次调用没有结果"本身是一个可
补写的记录，而不是一个缺口。

## 5. 存储

```kotlin
// 全局：每工具一个值，缺席即用内置默认
approval_defaults(toolName TEXT PRIMARY KEY, policy TEXT NOT NULL)

// 每 agent 覆盖：只能比全局严；缺席即无覆盖
agent_approval(conversationId TEXT, toolName TEXT, policy TEXT NOT NULL,
               PRIMARY KEY(conversationId, toolName))

// 每路径：路径相对会话目录，只能是文件或目录
path_policy(conversationId TEXT, relPath TEXT, policy TEXT NOT NULL,
            PRIMARY KEY(conversationId, relPath))
```

`relPath` 用**相对路径**而不是绝对路径：会话目录可以整体移动，绝对路径会失效。
裁决时必须走 `SessionWorkspace.resolve()` 得到规范化路径再比对——
**不能用字符串前缀匹配**，否则 `a/../b` 这类输入会绕过策略。

这与 05 的既有规则一致：`resolve()` 是路径变成 `File` 的唯一入口。
