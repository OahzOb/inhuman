# 用户自配云存储：备份镜像与会话同步 — 设计提案

> **状态：评估完成（2026-11-25），未实现，待拍板。** 建议拆成两阶段：
> **Phase 1 备份写进用户自己选定的同步文件夹**（S–M，先做）；
> **Phase 2 会话级双向同步**（L，等"真的两台设备交替用"再决定）。
>
> 前提：用户自己的存储，不是我们提供存储。App 不新增账号、不保存云凭据（Phase 1）；
> 云端只看到密文；agent 仍然没有网络——这是**应用功能**，和更新/日志上传同一层，
> 不是新的助手能力（`docs/08-port-philosophy.md` §1.2：app 代发请求 ≠ agent 有网络）。
>
> 实现时改：`docs/04-data-persistence.md`（备份一节）、`docs/07-gotchas.md`、
> `docs/13-product.md`（数据与恢复、未来规划）、`docs/README.md`（设备测试表）、根 `README.md`。

---

## 0. 结论先行

- **"同步"先拆成三个需求**：①灾备/换机恢复；②另一台设备看最新（单向）；③双设备双向合并。
  ①、②用 Phase 1 就能解决；③才是真正的"同步"，成本高且是产品决定。
- **Phase 1**：设置里选一个文件夹（SAF tree + 持久授权），"备份"直接写进去；上传由用户自己的
  Syncthing / Nextcloud / 网盘客户端完成。App 不联网、不存口令之外的任何凭据、云端只见密文。
  仍然由用户点一下触发——项目已经明确拒绝后台自动写备份（口令与保留策略未定）。
- **Phase 2**：要一种专门给同步用的会话文件（稳定 id、版本、tombstone），导入端支持"更新已有
  会话"；角色卡/场景必须随行；冲突保留两份显式副本，不做自动合并。成本 L。
- **不建议直连 WebDAV/S3**：那会是 App 的第一类云存储凭据 + 公共 HTTPS 网络代码 + 冲突处理，
  对大多数用户不方便，相对 Phase 1 没有优势。

## 1. 现状（代码事实）

### 1.1 加密备份（整库，替换语义）

- 内容：`VACUUM INTO` 的整库快照 + `manifest.json`（`format:1`、`databaseVersion`、
  `createdAt`）+ 整个 `filesDir/conversations/` 工作区树。
- 加密：AES-256-GCM，PBKDF2-HMAC-SHA256 210,000 次，magic `INHUMAN_BACKUP_1`；口令从不落盘。
- 排除：`SecureStore` 全部内容（API key、网页/媒体 key、OAuth token、SSH 地址簿、各类偏好）、
  rollback 快照、诊断日志。
- 目的地：单个 SAF 文件（`ACTION_CREATE_DOCUMENT`），用户选位置。也就是说**今天已经可以把
  备份存进任何系统文件提供器**，包括某些云盘 App；缺的是"记住位置、提醒后一键"。
- 恢复：解密校验到 staging，仅允许 `inhuman.db` 与 `conversations/*`；`InhumanApp.onCreate`
  在 Room 打开前换库，失败回滚，保留一次 Undo。**整库替换，不合并**。

### 1.2 单会话对话包（.zip）

- 内容：JSON + 附件字节，只带**当前分支**；不含 message id / parentId，不含助手、角色卡、场景
  （`ConversationBundle.FORMAT = "inhuman.conversation/1"`）。
- 导入：首页"新建 → 导入对话包"，**总是生成新对话并重发 UUID**。所以它适合"分享/搬运一段
  对话"，不能"更新已有会话"，也不能当同步。

### 1.3 明文导出与分享

单会话 Markdown（可选工具结果，附件只列路径）、系统分享面板、可选的 `/conversation` 上传
（明文、服务端无鉴权、仅 LAN/Tailscale）。产品文档明确：这是明文的出口，不能当备份。

### 1.4 数据模型里没有"同步"需要的东西

- `conversations` / `messages` 主键是 String UUID，应用内生成；但**没有** deviceId、tombstone、
  行级 `updatedAt`、修订号/内容哈希。
- 消息排序 `createdAt ASC, id ASC`，`createdAt` 取本机时钟；分支靠 parent 关系，而对话包
  刻意不带它。
- 附件字节在工作区（永久工作区可被多段对话共享，256 MiB / 5,000 文件配额），库里只存相对路径。
- 同一会话在两台设备各自续写，目前只能变成两段独立对话，没有任何字段可判分叉。

### 1.5 网络与凭据边界

更新、日志上传、对话上传都只在用户点击时发生，产品代码没有 WorkManager/定时任务；
`normalizeServerUrl` 只收 http/https，HTTP 仅私网、`*.local`、`*.ts.net`、Tailscale CGNAT。
每个功能各建 OkHttp 客户端，没有统一传输层。备份口令从不落盘，所以"自动备份"必然要么
存口令、要么放弃加密——这正是 `docs/04` 拒绝后台写入器的原因。

### 1.6 SAF 文件夹的现有基础

Files 的"从 URL 下载到文件夹"已经用过 `OPEN_DOCUMENT_TREE` +
`takePersistableUriPermission`，再用 `buildDocumentUriUsingTree` / `createDocumentUnique` 写
单文件（`FilesScreen.kt`）。Phase 1 可以复用这条路径，**不需要新的权限声明**。

## 2. Phase 1：备份写进用户自己的同步文件夹（建议先做）

### 2.1 机制

- 设置 → 备份：选一个文件夹（SAF tree，持久授权）；"备份"按钮把现有加密备份文件写进
  `<folder>/inhuman-backup-<时间戳>.<后缀>`；再次备份写新文件，不覆盖旧文件。
- 用户自己在该文件夹上运行 Syncthing / Nextcloud / 网盘客户端完成上传。App 不感知云厂商。
- 备份提醒（已有）到期时，点"立即备份"直接写入记住的文件夹，不再每次弹文件选择器。
- 换机/重装：用同一个文件夹里的备份文件走现有导入流程（预览 → 替换）。

### 2.2 为什么不直连 WebDAV/S3

- 会成为 App 的第一个云存储凭据（要进 `SecureStore`、要进"备份排除"清单、要新的泄露面）。
- 需要公共 HTTPS 地址、认证失败/重试/限流代码，和"用户点一下才发生"的现有节奏冲突。
- 大多数用户没有 WebDAV/S3，但有系统文件入口 + 某个同步客户端。
- SAF 方案让云厂商看到的是密文，且 App 完全不认识云。

### 2.3 改动面

- 设置：文件夹选择 + 持久授权 + 显示当前文件夹/上次备份时间；`BackupRepository` 支持 tree Uri
  输出（现为单文档 Uri）。
- 备份提醒的跳转目标改为"备份到已记住的文件夹"。
- 测试：Uri 构造与文件名是纯函数，可 JVM 测试；权限丢失（用户撤销授权）要有可读错误，
  不静默失败。
- 文档：04/07/13/README/根 README。

### 2.4 风险与要拍板的地方

- 备份体积 = 数据库 + 全部工作区，可能数百 MB；每次备份都是完整一份。**保留几份？**
  自动清理旧文件是"后台写"的变体，需明确规则（建议：不自动删，界面显示占用，用户自己删）。
- 云盘 App 是否提供 `DocumentsProvider` 不在我们的控制内；本地文件夹 + Syncthing 始终可用。
- 口令不落盘 → 不能免输入。这是 Phase 1 的边界，也是它安全的原因；不要为了"自动"存口令。

### 2.5 验收

- 选文件夹 → 备份 → 文件夹里出现加密文件；关掉应用再打开仍记得该文件夹。
- 用该文件走一次导入，数据与备份时一致。
- 撤销文件夹授权后按"备份"给出可读错误，其他功能不受影响。
- 没有新增网络请求、没有新增存储权限、agent 能力不变。

## 3. Phase 2：会话级双向同步（如果真需要）

### 3.1 格式

每段对话一个文件（`<conversationId>.inconversation`），包含：

- 稳定 id（会话、消息、parent 关系）——现有 UUID 可以直接用；
- 会话元数据：标题、`sessionMode`、`sceneJson`、模型/服务快照；
- 助手快照：名称、系统提示、`rpJson`（角色卡）——否则换机后 RP 场景没有卡；
- 消息行（含分支树）、附件的相对路径；
- 会话版本号 / 内容哈希 / 最后修改时间；
- 删除标记：单独一个 tombstone 文件（或目录清单），否则删掉的会话会被旧副本复活。

### 3.2 导入语义

- 按 id 匹配：不存在 → 新建；存在且本机版本较旧 → 更新；本机版本较新 → 跳过；
- **两端都改过** → 不合并，保留本机版本 + 把对方版本导入成"（同步冲突）"副本；
- 删除：本机删除落 tombstone；对方文件带 tombstone 且本机没改过 → 删除；改过 → 冲突副本。

### 3.3 角色卡与场景

RP 对话的卡在 `agents.rpJson`（对话按 agentId 引用），场景在 `conversations.sceneJson`。
同步文件必须自带卡/场景快照，导入时创建或匹配一个助手，否则换机后场景是断的。
这是内容，不是能力；但"导入会新建助手"这条要在界面里说清楚。

### 3.4 工作区附件

- 附件在工作区，永久工作区可被多段对话共享；把附件字节塞进每个会话文件会重复放大。
- 建议 Phase 2a 只同步**记录**（数据库行 + 卡/场景），不同步工作区字节；另一台设备上附件
  显示为"未同步"并如实说明。工作区单独同步是另一个功能（zip 已有，但没有增量）。

### 3.5 加密

现有对话包是明文，明文上云不可接受。同步文件应复用备份的 KDF + AEAD（口令由用户输入，
仍不落盘）；代价是每次同步都要口令，且不能后台自动。若用户接受明文（例如自己的机器间
Syncthing），可以作为显式选项，但默认加密。

### 3.6 成本与判断

L：新格式 + 导入更新路径 + tombstone + 冲突 UI + 加密 + 卡/场景随行 + 配额/大文件处理 +
设备验证。它同时是一个产品决定：**会话从"可分享的导出物"变成"有身份、可合并的对象"**。
在 Phase 1 落地、且用户确实两台设备交替使用同一批对话之前，不建议启动。

## 4. 不变量（两阶段都适用）

- agent 仍然没有网络；同步是 App 的用户操作，不是工具。
- Phase 1 不保存任何云凭据；备份保持加密，云端只见密文。
- 备份 = 替换语义，同步 = 合并语义，两者**不能互相冒充**：界面文案和文档必须说清。
- 恢复仍在 Room 打开前完成、失败回滚、保留一次 Undo。
- 不新增存储权限（SAF 授权即可）；不新增账号。

## 5. 待拍板

1. Phase 1 是否就够：目标是"换机恢复/灾备"还是"两台设备同时用"？
2. 备份保留策略：不自动删（建议）还是保留最近 N 份？
3. 是否接受 Phase 1 每次备份仍需用户点一下、且口令每次输入（不存口令）？
4. Phase 2 若做：附件不同步可以接受吗？卡/场景随行、导入时新建助手可以接受吗？
5. 是否永久放弃直连 WebDAV/S3（建议：是，直到有明确用户需求）？

## 6. 建议顺序

Phase 1（S–M）→ 用一段时间 → 只有"双设备双向"成为真实痛点时才评估 Phase 2（L）。
