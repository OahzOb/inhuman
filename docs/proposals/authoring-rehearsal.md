# 配置创作与试跑（Authoring + Rehearsal）— 主要需求

> **状态：提案，未实现（2026-11-27）。** 本文记录**主要需求与范围边界**，
> 不含实现计划、schema、验收标准或排期；这些等需求与边界确认后再展开。
> 现有行为以编号文档（`04` / `06` / `07` / `13`）为准。
>
> **2026-11-27 升格：本文的主要需求已成为项目原则**——"内容可以代写，行为不能代写"，
> 记录在 [08-port-philosophy.md](../08-port-philosophy.md) §1.8、[13-product.md](../13-product.md) #13
> 与根 `AGENTS.md`（"The agent authors content, never behaviour"）。原则约束所有未来
> 的配置类功能；本文仍是需求与可行性记录，机制未实现。
>
> 关联：[cast-run.md](cast-run.md)（多演员试跑底座）、[roleplay.md](roleplay.md)、
> [config-workshop.md](config-workshop.md)（工坊的读/起草/提案体系）、

> [08-port-philosophy.md](../08-port-philosophy.md)、[13-product.md](../13-product.md)。
>
> 词汇：**配置**（user-configurable content）是用户能改、且会影响模型行为或对话表现的
> 内容；**草稿**（draft）是还没保存的配置；**试跑**（rehearsal）是 agent 用草稿跑一次
> 隔离的模拟；**提案**（proposal）是现有"agent 起草、用户点保存"的卡片；**预算**
> 是一次创作会话允许花的请求数。

## 0. 结论先行

**用户不会写系统提示词，也不会配角色卡、世界书、场景。** 他们不该为了得到一份能用的
配置，先把 agent 的输出复制出去、手工填好、开一段对话试、发现不行，再截图粘贴回来。

所以主要需求是：**agent 代写配置、自己试跑、自己改，最后递上一份已经验证过的提案；
用户只在三处出现——提供它拿不到的信息、授权一次预算、最后点保存。**

范围是**整个 app 的用户可配置内容**（不只 RP）；边界是**不碰工具如何运行、权限、
授权、密钥和全局设置**。一句话：

> **内容可以代写，行为不能代写。**

## 1. 需求

### 1.1 用户原话（2026-11-27，转述）

- 用户可能不了解系统提示词是怎么被送进对话的，也不会下载、配置这些东西；
- RP 也一样：不知道该怎么配置世界书，不知道怎么写 prompt；
- 所以需要 agent 帮用户做这些事；
- agent 做这些事，就需要**及时得到第一手反馈**——不能是用户粘了 agent 的输出、
  费劲配好对话、才发现不好用，再回头复制粘贴或截屏给 agent；
- 主要目的是**省去沟通门槛**：agent 强就强在可以试错，这个技能如果加一层用户中转，
  效果会变得非常差；
- 范围是整个 app（不只 RP），但**仅限用户可配置的**；不会允许 agent 修改工具如何
  运行之类的 app 自身功能。

### 1.2 现状：人肉中转

今天的路径（以提示词/角色卡为例）：

```
agent 写一版 → 用户复制 → 用户进编辑器粘贴保存 → 用户开一段对话
→ 用户发现不对 → 用户截图/粘贴回来 → agent 再改 → ……
```

每一步都要人参与，而且**反馈是残缺的**：截图丢掉了 system 里真正发出去的内容、
世界书命中了哪几条、模型是在第几轮崩的。agent 在改一个它看不见结果的东西。

工坊的 proposal 体系已经把"先起草、用户点保存"做出来了
（`app_propose_assistant` / `app_propose_instruction` / `app_propose_prompt` /
`rp_create_scene`），但它只解决**保存**，不解决**验证**。

### 1.3 目标：agent 的试错闭环

```
用户说出目标（可能只有一两句话）
  → agent 起草配置
  → agent 用草稿跑一次试跑（模拟用户/场景）
  → 转录与失败点回到 agent 自己的上下文
  → agent 改，再跑，再改（预算内）
  → 交出一份"已经跑过、没失败"的提案
  → 用户点保存
```

人的位置只有三处：

1. **提供 agent 拿不到的信息**：目标、示例、真实案例、品牌语气、边界；
2. **一次预算授权**："这次创作最多花 N 次请求"——不是每次试跑都问；
3. **最后点保存**：沿用现有的提案卡，不自动写用户的配置。

### 1.4 边界：三档

| 档 | 内容 | agent 能做什么 |
| --- | --- | --- |
| **A. 可代写** | 系统提示词、角色卡文本、场景文本、世界书条目、提示词库条目、工作区根 `AGENTS.md`、名称/标题/描述这类纯文本 | 读、起草、试跑、提案；用户点保存 |
| **B. 只可建议** | 工具选择、服务商/模型、采样参数（温度等）、审批规则 | 可以说明"建议开/关哪个"，但**提案里不带这些字段**，也不能写；由用户自己在原编辑器改 |
| **C. 不可碰** | 工具如何运行、沙箱、权限模型、SSH/下载/抓取授权、密钥与 OAuth、全局设置、更新/服务器地址、数据库与代码 | 读都只读现状（多数连读都没有），**不写、不提案、不解释成可改** |

判据不是"这项有没有 UI"，而是：**改它会不会改变能力或行为**。会 → B/C；
只是一段会进入提示词的文字 → A。这与 `AGENTS.md` 的既有规则同构：
**内容不是能力**（角色卡、场景、`AGENTS.md` 都只进 system，不能加工具/审批/授权）。
B 档的划线（工具选择、服务商/模型、采样参数、审批规则）已于 2026-11-27 经用户确认。

## 2. 为什么不是 GM、也不是 subagent

- 这里的单位不是"一场戏"，是**一份草稿 + 一组测试用例**；
- 演员是**测试夹具**（愤怒的客户、不懂手机的老年用户、爱抬杠的审稿人），不是角色；
- 导演是**作者**，不是游戏主持人；它要的是"这版能不能用"，不是"故事好不好看"；
- 输出是**一份用户能直接保存的配置**，不是一段剧情。

GM 的框架（世界状态、裁定、叙事权）只在"用户真的想跑团"时才需要；本文的试跑不需要它。
多演员试跑见 [cast-run.md](cast-run.md)；单演员/单用例是它的子集。

## 4. 试跑机制（需要什么）

### 4.1 一个工具，而不是一个后台系统

```
trial_run(
  subject: 草稿配置,        // 提示词 / 卡 / 场景 / 世界书 / AGENTS.md，未保存也能跑
  cases:   [ { 模拟用户,  开场消息,  可选：期望/禁止 } ],
  rounds:  2,
  budget:  本次试跑允许的请求数
) -> { 渲染后的 system 摘要, 每个用例的转录, 失败点, 用量 }
```

- **草稿不落库**：不要求先保存半成品 assistant 才能试；
- **结果直接进 agent 上下文**：转录、实际渲染的 system/命中条目、失败点，都在工具结果里，
  agent 立刻能改下一版；
- **一次授权、多次迭代**：用户在一次创作开始时给预算（例如 20 次请求），
  agent 自己跑 2～3 轮；每次结果里带剩余预算，用完就停、把现有结果交出来；
- **零能力**：被试主体和模拟用户默认都没有工具、文件、网络；要测"会不会正确调用工具"时，
  用 **stub 工具**（预设输入/输出），绝不接真实工具——否则草稿里的注入就能动真东西；
- **可重放**：同样的草稿 + 用例 + 模型设置应该得到可比较的结果，方便"改一版再跑"。

### 4.2 证据与诚实边界

- 自评只能发现**明显失败**：跑题、越界、格式坏、语气不对、泄露设定、该问不问；
- 证明不了"好"。证据要写成"这 N 个用例没有失败"，不是"已经完美"；
- 结果卡里固定写明"这是模拟，不是真实使用的证明"；用户仍可在真实对话里试。
- 每次试跑都计入用量（现有 usage 体系），按创作会话记账。

### 4.3 隐私与诊断

- 试跑内容都是用户内容，留在本地；诊断日志只记形状（用例数、轮次、用量、失败类型），
  不记提示词、转录正文——与 `10-diagnostics.md` 一致。

### 4.4 与 cast-run 的关系

- 单演员 / 单用例：本提案的最小形态；
- 多演员（模拟用户、评审小组、多人格互动）：用 [cast-run.md](cast-run.md) 的演员、
  转录、预算和 Stop；cast-run 的"导演"在这里就是**作者**；
- RP 场景的多角色群聊是同一底座的另一个用途，不是本需求的前提。

## 5. 与现有机制的关系

- **工坊**：已经有"读配置 + 起草 + 提案卡"三件套，且提案不带工具/服务商/模型/审批字段
  （[config-workshop.md](config-workshop.md)）。本提案只加**试跑**这一件，不改变提案的权限形状。
- **提案卡**：保存路径不变；变化是提案里可以附一段"试跑结论"（哪些用例跑了、哪些失败过、
  最后一版是否仍然失败）。
- **cast-run**：提供多演员、转录、可见性、预算；本提案是它的**主用例**。
- **goal**：未来可以让"长时间自动创作"走 goal 轮；本提案不依赖它。
- **不新增能力**：试跑不读写工作区之外、不联网、不执行；草稿是内容，不是能力。

---

## 6. 安全与不变量

1. **内容不是能力**：任何被代写的配置仍然只是文本，不能加工具、审批、授权或网络路径。
2. **保存永远由用户点**：agent 不静默写用户的配置；提案卡是唯一入口。
3. **草稿只存在于试跑里**：试跑结束不落库；用户保存的只有他点过的那一份。
4. **试跑零能力**：主体与模拟用户没有真实工具/文件/网络；工具行为用 stub 验证，不用真实工具。
5. **B/C 档不可代写**：工具选择、模型/服务商、采样参数、审批、授权、密钥、全局设置
   不进入草稿、不进入提案；agent 只能建议，用户自己改。
6. **预算硬上限**：一次创作的请求数由用户授权，用完即停；不许后台偷跑。
7. **证据不夸大**：结果卡写明"模拟不是真实使用"；不把"没失败"说成"好"。
8. **诊断不记内容**：与 `10-diagnostics.md` 同一条规则。

---

## 7. 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 成本 | 迭代是 N 次请求，agent 可能改很多版 | 一次授权 + 硬上限 + 每次结果显示剩余预算 |
| 自评偏差 | 模型给自己打分，可能"看起来通过" | 用例要具体、有行为断言；标明模拟；用户可看转录 |
| 草稿质量 | agent 写出一份"测试能过、真实场景不行"的配置 | 用例来自真实材料/用户描述；最终仍可在真实对话验证 |
| 越权 | 把"建议"做成"静默改设置" | B/C 档硬边界：不进入草稿与提案字段 |
| 注入 | 用户/外部材料是 untrusted | 试跑零能力 + stub 工具；结果按数据引用 |
| 预算滥用 | agent 反复试跑烧钱 | 授权一次但封顶；结果里显示剩余；Stop |
| 配置漂移 | 用户保存后自己又改，试跑结论过期 | 提案卡记录试跑时的版本/时间；不做长期缓存 |

## 8. 待定问题

1. **预算**：一次创作会话的默认请求数、上限、是否可分次追加？
2. **试跑默认开/关**：工坊里自动允许，还是用户先开？
3. **世界书**：存放位置（工作区文件 / 应用内编辑器）、编辑入口、可见性字段怎么填。
4. **用例从哪来**：用户口述？工作区素材？agent 自己造？要不要"期望/禁止"断言？
5. **试跑结果留多久**：只进当轮上下文，还是作为提案附件持久化（用户可回看）？
6. **B 档"建议"的呈现**：只在文字里说，还是也做成一个不可点的建议条？
7. **多演员**：什么时候从单演员升级到 cast-run（用例数超过 N？需要多个模拟用户？）。

---

## 9. 建议顺序

1. **先补"验证"这一段**：`trial_run` 单主体、单用例、单轮（用草稿跑一次，转录回 agent）；
2. **多用例 + 迭代预算**：一次授权、多次试跑、结果带剩余；
3. **接进工坊**：assistant / 提示词库 / `AGENTS.md` 三类内容先接；
4. **世界书**：内容模型 + 程序化命中 + 试跑（见 [cast-run.md](cast-run.md) §3.3）；
5. **多演员试跑**：cast-run 的演员/转录/Stop；
6. **RP 场景**：卡与场景的试跑，和多人格群聊。

每一步都单独可用：第 1 步就能把"复制粘贴截图"这个循环去掉一大半。
