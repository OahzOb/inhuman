# RP 创作助手 — 设计提案（以及为什么不做通用个人助理）

> **状态：评估完成（2026-11-25），未实现，待拍板。** 建议做两件小事：
> **①内置「RP 创作助手」模板**（一个普通助手 + 固定系统提示，成本 S）；
> **②角色卡/场景的 JSON 导入**（真正解除"不会填"的一步，成本 S–M）。
>
> **不建议**借这个需求做通用个人助理（`continuous-session.md` §16.1 里的 B）。
> 它需要跨对话记忆作用域、用户数据读取授权和写入规则，RP 创作一个都不需要。
>
> 实现时改：`docs/13-product.md`（角色扮演场景与助手）、`docs/06-agent-loop-ui.md`
> （如果加"导出到工作区"）、`docs/07-gotchas.md`（导入校验的边界）、`AGENTS.md`
> （RP 是内容不是能力那条旁边加"创作助手只是助手模板"）、`docs/README.md`（文件归属表）。

---

## 0. 结论先行

- 用户的痛点是"RP 内容我自己不会填"，缺的**不是**一个助理，而是一条
  **模型输出 → 卡/场景编辑器**的导入路径 + 一套好提示词。
- 一个"创作助手"就是一个**普通助手**：固定的系统提示要求它访谈、输出严格 JSON、把文件写进
  工作区；工具用现有的文件工具。不新增工具、不新增权限、不碰跨对话记忆。
- 卡/场景现在只能手填；`RoleplayCodec` 已经有解析和字段校验，只是没接到 UI。补一个
  "粘贴 JSON / 从文件导入"，并在保存前做字段级校验和预览。
- 明确不做：agent 读写 app 数据库、跨对话读记录、自动创建卡/场景/对话、内置一个出厂助手行、
  编辑器里的"AI 一键生成"按钮。前者越能力边界，后两者是不必要的第二条请求路径。

---

## 1. 现状（代码事实）

### 1.1 卡/场景只能手填

- 角色卡 7 个文本字段 + 3 个采样参数；场景 5 个字段；上限 16 KiB / 10 KiB 及逐字段上限
  （`core/engine/.../roleplay/Roleplay.kt` 的 `RoleplayCard` / `RoleplayScene` / `RoleplayLimits`）。
- 卡编辑器、新建场景对话框、场景设置都只有表单字段，**没有导入**；`docs/proposals/roleplay.md`
  也把 JSON/PNG 卡导入明确列为未做。
- `RoleplayCodec.decodeCard` 目前只用于从数据库读音（`AgentsViewModel`），不接用户输入。
- 对话包不含角色卡和场景（`ConversationBundle` 的字段里没有），所以"把一段 RP 对话搬到
  另一台设备/另一个安装"会缺卡，这是导入/导出方向要一起考虑的。

### 1.2 模型写不到 app 数据

- `Tool` 接口没有数据库/仓库句柄；文件工具只拿工作区相对路径，受配额和路径围栏约束。
- 唯一读记录的工具是 `recall`：只读当前对话的活动分支、结果不落全文、不跨对话。
- 修改 agents/conversations 只有 UI 路径；agent 不能给自己加工具，也不能改角色卡。
- 这些边界是对的，本提案不松动任何一条：**创作助手只能写工作区里的文件**，由用户手动导入。

### 1.3 之前关于个人助理的决定

- `continuous-session.md` §16.1：先做 A（持续会话），B（跨对话持久助手）和 C（RP 持久化）
  其后做；跨对话记忆明确不是 A 的一部分，隐私/注入/工作区边界都要重新回答。
- `roleplay.md` §16.1：本轮只做 RP，不做个人助理（B）；但这是**推迟**，不是永久否决。
- 本提案不重新打开 B：它提出的形态不是"一个记得所有对话的助理"，而是"一个把角色卡写好、
  把文件交给用户的普通助手"。

### 1.4 辅助补全的先例

`suggest_replies` 证明"主回合之外的一次额外请求"可以存在：助手配置建议模型、只带最后一问一答、
有超时、失败静默、结果落库、点一条只填输入框。它的存在让"编辑器里加一个 AI 生成按钮"在技术上
可行，但会变成第二条需要披露/计费/错误处理的请求路径；在聊天路径可用时不做。

## 2. 把需求拆开

| 需求 | 是否需要新能力 | 本提案怎么做 |
| --- | --- | --- |
| 写角色卡（身份/性格/说话方式/开场白/示例对白/边界） | 否，纯文本 | 模板助手产出 JSON，用户导入卡编辑器 |
| 写世界与场景（世界、情境、用户扮演谁、叙事格式） | 否，纯文本 | 同上，场景 JSON 导入或从卡预填 |
| 写剧情/大纲、维护连续性 | 否 | 助手在工作区写 `rp/剧情大纲.md`；用户把旧 transcript 导出进工作区后它可读 |
| "管理我的 RP 会话"（读所有对话、改卡） | **是**（跨对话数据） | **不做**；见 §6 |

## 3. 方案 1：内置「RP 创作助手」模板

### 3.1 它是什么

AgentsScreen 的新建入口增加"从模板新建"，模板是代码里的一个常量（名称 + 系统提示 + 默认工具），
**不**在数据库里 seed 一个助手行：

- 不在升级时凭空多出一个助手（用户会问"这是谁、能删吗"）；
- 模板改动随版本走，不会和用户改过的行冲突；
- 用户从模板创建后得到的是一行普通助手，之后完全可编辑、可删除。

### 3.2 系统提示的要点

- 目标：帮用户产出可直接导入的**角色卡 JSON**与**场景 JSON**，字段与上限对应当前 schema。
- 流程：先问 3–5 个关键问题（题材、角色与用户的关系、用户扮演谁、语气/尺度、是否已有设定），
  给一版初稿，再按反馈迭代；不要一次抛二十个问题。
- 输出：把 JSON 写进工作区 `rp/角色卡-<名字>.json`、`rp/场景-<名字>.json`，文件内容只放 JSON；
  在聊天里给人类可读摘要（性格、开场白、边界、还缺什么）。
- 约束：不要编造用户没说的设定；缺省字段留空并说明；角色卡 ≤16 KiB、场景 ≤10 KiB；
  已有卡 JSON 传入时按其字段续写，不丢字段。
- 工具：文件工具（读/写/列目录）即可；不选付费、远程、下载，也不选 recall（它只读当前对话，
  对创作没有意义）。

### 3.3 工作区

建议让用户把创作对话绑定到**永久工作区**（或从模板创建时提示），这样产出的卡文件在对话删除
之后还在；用户也可以反复回来改。助手看到的始终只有这个工作区——这正是"只看到你递给它的东西"。

### 3.4 改动面

AgentsScreen 新建菜单 + 模板常量 + 测试（模板提示里出现字段名/上限、工具集合正确）；
文档改 13/AGENTS/README。成本 S。

## 4. 方案 2：卡/场景 JSON 导入（真正解除痛点）

### 4.1 入口

- 角色卡编辑器：新增"导入 JSON"——**粘贴**与**从文件选择**两个入口（SAF `OpenDocument`，
  不需要新权限）。粘贴是最低成本的路径：聊天里的 JSON 复制过来即可。
- 新建场景对话框：导入场景 JSON，或"使用角色卡的默认场景"（卡里已有该字段时预填 5 个场景
  字段；没有就留空）。
- 场景设置对话框（已有对话）：可导入场景 JSON 覆盖当前场景，保存时仍走现有校验。

### 4.2 校验与预览

- 复用 `RoleplayCodec.decodeCard` / `decodeScene` + `RoleplayLimits`；解析失败给字段级错误，
  不要只显示"格式错误"。
- 导入只**填进表单**，显示将覆盖哪些非空字段；用户仍要点保存。导入不是"直接写入数据库"，
  这样误粘贴一份错卡不会静默毁掉现有配置。
- 外部 JSON 当不可信文本处理：长度上限、未知字段忽略并提示、字段超限截断或拒绝（与
  `RoleplayCodec` 的现有规则一致）。

### 4.3 改动面

RoleplayCardEditor 增加粘贴/文件对话框；NewSceneDialog 增加导入与卡预填；解析失败文案；
测试：合法卡/场景、缺字段、超限、未知字段、空文件。成本 S（粘贴）/ S–M（文件选择器）。

## 5. 可选：导出到工作区与剧情大纲

- 对话菜单增加"导出到工作区"（当前对话 Markdown 或对话包写进本对话/永久工作区的目录）。
  它只是**复制**，不扩大助手能看到的范围：助手只读它所在的工作区。
- 这样"创作助手"可以在同一个工作区里读旧 transcript，维护 `rp/剧情大纲.md`（人物关系、
  未决线索、连续性），把"管理剧情"变成工作流而不是新能力。
- 已有替代：导出到系统存储 → 在 Files 里导入工作区，多几步。本轮可不做。

## 6. 明确不做：通用个人助理

### 6.1 PA 的前置条件

`continuous-session.md` §16.1 的 B 要回答的是：跨对话记忆的作用域（哪些对话共享）、
用户数据的读取授权（agent 能不能读 transcript、读哪些）、写入规则（能不能改卡、改场景、
改助手）。这三个问题都不小，且每一个都会改变"助手只看到工作区"的一句话声明。

### 6.2 为什么这个需求不需要它

- 创作是**单次、有界**的：一段创作对话产出一份文件，用户导入，结束。没有"记得上一次创作"
  的硬需求；需要延续时，把旧文件留在工作区即可。
- "管理 RP 会话"若指读 transcript / 改卡，恰恰是 6.1 的跨对话能力，**不是**创作需要的。
- 做了 PA 会引入新的披露、授权和审计面，而当前痛点只需要一条导入路径。

### 6.3 如果将来要做

单独设计（`docs/08-port-philosophy.md` §1.2/§1.5、Q4 都要回答）：先定义作用域，再定义读取
授权，最后定义写入规则；不要把它伪装成"RP 的顺带功能"，也不要让 RP 的卡/scene 变成它的
数据入口。

---

## 7. 不变量

- RP 是内容配置，不是能力：卡/场景只进提示词，不改变工具、审批、SSH、工作区边界。
- 模板助手是**普通助手**：不新增加载器、不新增隐藏开关、不 seed 行。
- 导入只填编辑器，保存仍是用户动作；模型不能写 agents/conversations。
- 外部 JSON 与模型产出都当不可信文本：校验、限长、不执行。
- 诊断日志不记录提示词、文件内容、卡/场景内容。

## 8. 待拍板与验收

**待拍板**：

1. 模板入口放哪里（AgentsScreen 新建菜单里的"从模板新建" vs 单独按钮）？模板名称与语言？
2. 导入先做"粘贴 JSON"够不够，还是要同时做文件选择器？要不要兼容 SillyTavern 的字段名
   （第一版建议只认本项目 schema，映射另做）？
3. 场景导入做成"导入 JSON"还是只做"从角色卡默认场景预填"？
4. 是否本轮做"导出到工作区"（剧情大纲工作流的关键一步）？
5. 要不要内置 1–2 张示例卡作参考（会占用户卡库，需可删）？

**验收**：

- 从模板新建 → 对话 → 产出 `rp/角色卡-*.json` → 卡编辑器粘贴/导入 → 预览 → 保存 →
  新建场景 → 开场白正常出现（`finishReason = "stop"`，不显示"继续"）。
- 导入超限/缺字段的 JSON 给出可读错误，且不覆盖当前表单。
- 不新增工具、权限、网络路径；手机与平板两种窗口实际验证。
