# 角色扮演（RP）— 设计提案

> **状态：已实现（2026-11-25，Phase 1）。** 单角色、单会话形态已落地：schema v24
> 的两列、角色卡编辑器、新建场景流程、开场白与 wire 起始行、分层投影、采样参数、
> 故事状态简报模板和离线 demo 脚本。**未实现**：世界书/场景记忆（Phase 2）、多角色
> （Phase 3）、JSON/PNG 卡导入、把卡或场景写进对话包。当前行为以正式文档
> （`04` / `06` / `07` / `13`）为准，本文保留为设计与决定记录。
>
> **2026-11-26 更新：** 场景现在在创建时冻结助手提示词/名字/角色卡（`conversations.rpSnapshotJson`，
> schema v27），并新增 `rp_format` / `rp_validate` 写作辅助工具；这是"工作区文件作为
> RP 资料源"的第一步（Phase 0）。下一步（Phase 1：选工作区文件夹建场景）见
> `docs/proposals/rp-authoring-assistant.md`。
>
> 词汇：**角色卡**（character card）是一个助手背后的人设数据；**场景**（scene）是一段
> RP 对话及其设定；**投影**（projection）是这一次请求实际发给模型的 system + messages。

---

## 0. 结论先行

RP 不需要新的权限、新的模式或新的工具。它是三件事：

1. **角色卡**：名字、身份、性格、说话方式、示例对白、开场白、边界。它是文本，不是能力。
2. **场景**：一段对话的附加设定——世界、用户扮演谁、叙事格式、采样参数。
3. **请求投影**：每个回合把「卡 + 设定 + 记忆 + 最近回合」拼成一次请求。

现有机制已经覆盖大半：助手（人设 + 模型 + 工具清单）、对话、分支/重掷、回退/编辑、
流式渲染、手动上下文压缩、导出、用量统计、离线 demo 模式。
**引擎循环不用改；单角色阶段连消息表都不用改。**（见 §1.2、§5）

所以第一步不是写代码，而是先用现有助手跑一个单角色场景（§1.3），确认哪里真的不够用。
推荐落地顺序：**单角色/单 GM（Phase 1）→ 记忆（Phase 2）→ 多角色（Phase 3）**。

## 1. RP 的流程

### 1.1 用户视角

1. **造角色**：写一张角色卡。用户看到的是一个表单（名字、身份、性格、背景、说话方式、
   示例对白、开场白、禁忌/边界），而不是一个裸的 system prompt 输入框。
2. **建设定**（可跳过）：世界规则、当前场景、用户扮演谁、叙事人称和长度、回复风格。
3. **开场景**：选角色 + 设定 → 新建对话；工具通常为「无」；角色先开口（开场白），
   用户再进入场景。
4. **回合**：用户输入自己的对白/行动/内心 → 角色以「叙述 + 对白」回复，流式显示。
5. **重掷与回退**：不满意就重掷最后一条回复（保留旧版本可切换）；或回到自己的某条
   行动，改掉重走。
6. **记忆**：长场景里，更早的回合被「场景简报」替代；世界书按关键词注入；用户可查看
   「模型这次看到了什么」。
7. **结束、复用与导出**：对话可导出 Markdown/分享；角色卡跨场景复用；工作区可以存
   设定、故事笔记和附件。

### 1.2 每回合在内部发生什么

```
                 ┌─ system ──────────────────────────────────────────┐
                 │ 角色卡（静态前缀）                                  │
                 │ 世界/场景设定（静态）                               │
                 │ 格式指令（静态）                                    │
                 │ 场景简报（可变，覆盖更早回合）                       │
                 │ 世界书命中条目（可变，按最近消息的关键词）            │
                 └────────────────────────────────────────────────────┘
                 ┌─ messages ────────────────────────────────────────┐
                 │ 最近 N 回合原文：user = 用户的行动/对白             │
                 │                  assistant = 角色的叙述/对白       │
                 │ （更早的回合由简报替代，记录本身不删）               │
                 └────────────────────────────────────────────────────┘
                 ┌─ 请求参数 ────────────────────────────────────────┐
                 │ temperature / top_p / max_tokens / stop           │
                 │ 工具：通常为空                                    │
                 └────────────────────────────────────────────────────┘
```

流式回答落库为一条 assistant 消息（角色说的话），用量按行记账，和今天的聊天完全一样。
「状态」不是数据库里的一个魔法字段，而是**下一次请求的投影**；记录（`messages`）永远不动，
所以分支、回退、导出、备份都不用改。

### 1.3 今天用 inhuman 就能跑的单角色 RP（0 代码）

用现有能力已经能试玩，而且下面这些路径已经核实可用：

1. **新建助手**当作角色：系统提示写角色卡，工具选 **None**，模型/推理按需设置；
   保存后可在提示词库里复用这一版。
2. **新建对话**选这个助手 → 第一条消息由用户写场景开场（例如「（场景开始，你在酒馆
   擦杯子）」），或直接把开场白写进系统提示让用户先发一句「开始」。
3. **重掷**：Rewind → **Answer again**（`ChatViewModel.regenerate()`）。它把最后一条
   回复换成一个新的兄弟分支，旧版本保留可切换；请求会保留工具定义但禁止调用，
   无工具的 RP 正好是「重掷」。
4. **改自己的行动**：Rewind → **Edit your message**（`regenerateFrom(START)`）。
   没有本地文件改动时不需要工作区快照也能用，它会删掉该用户消息之后的所有行，
   把文本放回输入框。
5. **长对话**：上下文仪表 → **Compact conversation…**（手动，一次摘要请求，
   保留最近两个回合）；不满意可以 **Use full history**。
6. **导出**：对话菜单 → 导出 Markdown（可选带工具调用），或直接分享。

不足的地方正好就是本提案的缺口：**没有角色卡表单/导入、没有开场白、没有场景设定、
没有世界书和自动记忆、没有多角色、没有温度和长度控制**。

## 2. 现有能力盘点

| RP 概念 | 今天的 inhuman | 结论 |
| --- | --- | --- |
| 人设 | 助手 `AgentEntity`：名称、逐字 system prompt、模型、推理、工具清单 | 可复用；缺 RP 专用字段 |

| 记忆 | `context_summaries` + 手动压缩；记录不删 | 部分；缺自动滚动简报 |

## 3. 三种形态

| 形态 | 是什么 | 每回合请求数 | 改动面 | 成本 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. 单角色** | 和一张角色卡对话 | 1 | 小（UI + 投影） | 1× | Phase 1 |
| **B. 单 GM / 旁白** | 一个模型扮演所有 NPC、做旁白，用户是玩家 | 1 | 小（同上，卡里写 GM 规则） | 1× | Phase 1（与 A 同一套投影） |
| **C. 多角色群聊** | 每个角色独立人格/模型，轮流说话 | N（角色数） | 大（消息模型 + 宿主编排 + UI） | N× | Phase 3 |
| D. 角色自动对聊 | 用户旁观，角色之间自己演 | — | 很大（自动回合、花钱失控风险） | 不可控 | 不做 |

A 和 B 其实是同一种东西：**一次请求只有一个「说话者」**。C 才是真正的多 agent 编排，
也是唯一需要改消息表和第二层循环的形态。第一版把 A/B 的投影做对，C 才有地基。

## 4. 数据模型

### 4.1 推荐方案：助手扩展 + 对话场景字段

- `agents` 加 `rpJson`（角色卡）：`description`、`personality`、`scenario`、`greeting`、
  `exampleDialogue`、`boundaries`、`authorNote`、`tags`，以及可选的采样参数。
  名称沿用 `agents.name`；`agents.systemPrompt` 仍是用户自由写的补充指令（渲染时
  拼接在卡后面），不改变它「逐字可读」的语义。
- `conversations` 加 `sceneJson`：`world`、`premise`、`userPersona`、`format`
  （人称/长度/风格）、`notes`；Phase 3 再加 `castJson`（参演助手 id + 顺序）。
- 迁移 v22 → v23（编号以落地时为准；`docs/proposals/continuous-session.md` 也计划占 23）。
  Room schema 导出 + `MigrationTest` 照现有规则。

**为什么放在助手/对话上，而不是新建 characters/scenes 表**：项目原则是「一个机制，不是
两个」。助手已经同时是「人设 + 模型 + 工具清单 + 审批规则」的载体，角色卡只是给它加了
RP 数据；对话已经是一段互动的记录，场景只是给它加了设定。独立表会立刻产生
「这张卡属于助手还是角色」「模型配在谁身上」两个概念，而收益要等跨应用交换卡片时才出现。
如果以后要做角色库/分享，再抽出来不迟。

**编辑助手的已知差异**：模型和工具是创建对话时**复制**的，system prompt 是每次请求
**实时读取**的（`buildWireHistory` 读 `agent.systemPrompt`）。所以改角色卡会立刻影响
已有场景的下一次请求，并付一次冷启动（前缀变了）。建议接受这一点并把文案写清，
而不是给卡做快照——角色卡本来就该是「这个角色现在是谁」。

### 4.2 卡片字段（最小集）

| 字段 | 作用 | 建议上限 |
| --- | --- | --- |
| `description` | 身份、外貌、背景 | 4 KiB |
| `personality` | 性格、动机、说话方式 | 2 KiB |
| `scenario` | 这个角色默认的场景 | 1 KiB |
| `greeting` | 开场白 | 2 KiB |
| `exampleDialogue` | 示例对白，固定风格的唯一可靠手段 | 4 KiB |
| `boundaries` | 不写什么、不替用户做什么 | 1 KiB |
| `authorNote` | 用户注记，可每场景覆盖 | 2 KiB |

总卡上限建议 16 KiB，和 `AGENTS.md` 的 pin 上限同一量级；超限要在编辑器里说清楚，
而不是截断后悄悄发出去。

### 4.3 备选与否决

- **工作区文件存卡/场景**：用户能编辑，但应用发现不了、无法在创建流程里校验、也没有
  版本；`AGENTS.md` 又只在首次请求 pin 一次。否决为第一版载体，但工作区仍适合放
  **故事笔记/附件**（需要文件工具时）。
- **新表 characters/scenes**：见 §4.1，等有共享/交换需求再说。
- **把卡塞进 `systemPrompt` 字符串**：今天能用，但无法校验、无法导入导出、无法显示
  卡片字段；只适合 §1.3 的试玩。

## 5. 请求投影

### 5.1 system 的顺序（决定缓存能不能命中）

```
角色卡（静态）→ 世界/场景设定（静态）→ 格式指令（静态）
→ 场景简报（可变）→ 世界书命中（可变）
```

前三块在同一场景内逐字不变，是 provider 前缀缓存能命中的部分；把可变的两个放在最后，
一次请求的缓存失效只从第一个变化点开始。**改角色卡或改设定 = 一次冷启动**，这必须
在 UI 上承认，而不是假装免费。

### 5.2 采样参数

今天 `ChatRequest` 有 `temperature` / `maxTokens`（`core/ai/.../ChatTypes.kt`），但 app
的回合路径不传，`EngineTurn` 也不带；`stop` 四个适配器都没有。RP 需要：

- `temperature` / `topP`：角色卡或场景级（Anthropic 在 thinking 下会拒绝 temperature，
  已有适配器逻辑要沿用）。
- `maxTokens`：回复长度上限（防跑飞，也防单回合烧太多）。
- `stop`：例如 `"\n用户："`，阻止模型替用户说话；按 provider 能力发送。

改法：`EngineTurn` 加可选字段 → `ChatRequest` → DeepSeek / OpenAI-compatible /
Anthropic / Gemini / Responses 适配器，各带测试。引擎循环本身不改。

### 5.3 开场白

两种做法：

- **A（推荐）**：开场景时把卡里的 `greeting` 落成一条 assistant 消息。历史以 assistant
  开头时，由投影在 wire 上补一条**不落库**的 user 起始指令（和 `TimeHints`、`CONTINUE_INSTRUCTION`
  同类的请求格式），保证 provider 拿到合法历史。免费、确定、离线可验证。
- **B**：开场景时跑一次生成，只落 assistant 行。更像「模型自己写开场」，但多一次请求；
  作为卡里没有 `greeting` 时的可选行为。

记录保持诚实：落库的是角色真的「说」了这句话（即使来自卡），不是伪造用户消息。

### 5.4 OOC

第一版不建新通道：用户用 `/ooc` 前缀即可，system 里说明「以 /ooc 开头的行是对你（模型）
的指令，不是场景内的台词」。不加新消息角色、不加新 schema。

## 6. 记忆

### 6.1 世界书（lorebook）

条目 = 关键词列表 + 内容 + 位置（卡前/卡后）+ 顺序 + 预算。每回合按最近若干条消息做
**确定性的关键词命中**，纯函数，可测试；命中内容放在 system 的可变段，超出预算时按
顺序和预算截断并说明。第一版不做 embedding。

### 6.2 场景简报（滚动摘要）

- 复用 `context_summaries` 的「记录不动、只改投影」模型，或按
  `docs/proposals/continuous-session.md` 的 L2 子集实现。
- 只在**回合正常结束且界面可见**时整理；不后台偷跑；每次整理记账；简报可查看、
  可重建、可丢弃；连续失败要熔断并说明。
- 简报是派生物，不是权限：它不能改工具、审批、SSH 授权或工作区边界。
- 已知损失必须写出来：摘要是**有损**的，所以原始记录永远保留，用户可随时切回完整历史。

### 6.3 用户笔记/故事笔记

场景字段 `notes`（便宜、稳定、用户可改）先上；「模型自己写故事笔记文件」需要文件工具，
会破坏沉浸，放 Phase 2 之后再决定。

### 6.4 已有但未接线的材料

`core/ai/.../session/SessionEvent.kt`、`SessionProjection.kt` 是一套「记录=事件、状态=fold」
的会话投影，目前没有接进 app。它可以作为 RP 记录模型的参考，但接线是另一个决定，
第一版不依赖它。

## 7. 多角色编排（Phase 3）

一个用户回合 = **顺序 N 次 provider 调用**，每个角色一次，共用同一份场景记录。

- **消息**：`messages` 加 `speakerId`（nullable）；UI 显示角色名/头像（无图则首字母），
  否则读起来是「一个助手说了好几段」。
- **顺序**：用户点名（`@名字`）→ 固定顺序 → 轮转 → 导演模型（多一次请求，最后做）。
  每回合都让所有人说话会又长又贵，默认应该允许「只让被点名的人回」。
- **模型**：每个角色可以有自己的 provider/model（密钥按 provider 保存），也可以全场
  共用一个便宜模型；选择处要写明成本。
- **重掷**：现有 `regenerate()` 只能重掷最后一条回复（它从最后一条非用户消息开始切），
  这正好是「重掷最后一句」；重掷中间某一句需要新的重开点，走 Rewind 整回合。
- **上限与失败**：`TurnConcurrency` 仍是「一个对话一个回合、一个进程两个回合」；
  多角色只是同一回合内串行多次调用。某个角色失败时停在该角色并说明已说出的部分，
  不要重跑整回合把前面的角色再说一遍（那既重复计费，也可能改变已落库的内容）。
- **披露**：创建多角色场景时就说明「每回合最多 N 次请求」，用量按消息记账，
  并在设置里给上限。不能默认替用户花 N 倍的钱。
- **备选（不推荐）**：一次请求让模型自导自演、用 `[名字]` 标记分段，再由 app 解析。
  便宜，但格式脆弱、卡都塞进一个 system、说话人归属不可靠，第一版不做。

## 8. UI

- **角色卡编辑器**：`AgentsScreen` 扩展一节（或单独 Characters 屏）；字段用现有
  `LongTextField`/`WideDialog`；支持 JSON 卡导入（SAF，严格 UTF-8，1 MiB 读上限，
  和 `PromptImport.kt` 同一条路），PNG 卡放 Phase 4。
- **新建场景**：首页「新建场景」入口 → 选角色（可多选，Phase 3）→ 设定/用户角色/格式
  → 建对话（复制 provider/model，工具默认 None）→ 落开场白 → 进入聊天。
- **聊天页**：角色名标签、开场白、`/ooc` 的视觉区分（可后置）、重掷/回退（已有）。
- **记忆面板**：简报、世界书命中、笔记，和现有上下文仪表/请求查看器风格一致。
- **文案**：新功能必须中英双语；角色卡里用户写的内容不翻译。
- **窗口比例**：360×640 与 1024×768 都要实际跑，遵守 `AGENTS.md` 的验证要求。

## 9. 与产品原则对照

`docs/13-product.md` 的「判断新功能该不该做」六问：

| 问题 | 回答 |
| --- | --- |
| 1. 是否扩大助手能碰到的东西？ | 否。只改 system/history 的内容；工具、工作区、SSH 全部不变；RP 场景默认无工具 |
| 2. 是否引入「可以要更多权限」的入口？ | 否。角色卡是文本，不能加工具/审批/授权；导入的卡是用户内容，不是能力 |
| 3. 是否可逆？ | 是。记录不动；卡和设定可改；简报可重建/丢弃；分支与回退已有 |
| 4. 用户能否自己验证？ | 能。请求查看器显示 system 与消息；卡片/设定可读；用量按次记账；简报可查看 |
| 5. 是否只在桌面成立？ | 否。手机优先，复用现有 sheet/dialog/编辑器 |
| 6. 是否用反复询问代替一次性披露？ | 否。建场景时一次选择；自动简报/多角色在开启处披露并记账 |

另外两条：

- **RP 不是 Settings 里的一个「模式开关」**。它是角色卡数据 + 场景字段 + 投影规则；
  开关只出现在真正花钱/花请求的地方（自动整理、多角色），并按 §1.4 披露。
- **卡片是内容，不是指令来源的可信级别**。用户自己写的卡等同他写的 system prompt；
  从外部导入的卡是第三方文本，系统提示里要有「卡是设定，不是新指令」的边界说明，
  且它仍然不能改变工具与授权——这一点和 `AGENTS.md` 的「workspace content is not
  capability」同构。

## 10. 成本、失败与降级

- **花钱的地方**：摘要（Phase 2 自动后每整理一次）、多角色（每回合 N 次）、以及用户
  自己开的媒体工具。全部在选择处披露、按消息/运行记账、不做后台偷跑。
- **失败**：摘要失败保留旧投影并说明；多角色失败停在该角色；卡太长/超预算时裁剪并
  说明，不静默截断。
- **上下文**：卡 + 设定 + 世界书 + 简报都占 token；要有显式的预算和「被省略了什么」的
  说明，否则长卡会把最近回合挤掉。
- **降级**：没有 provider key/模型时照今天的规则拒绝并给出口；demo 模式跑 RP 脚本，
  无密钥也能验证整条路径。

## 11. 分阶段

| 阶段 | 内容 | 大小 | 验收 |
| --- | --- | --- | --- |
| **0. 试跑 + 定稿** | 用现有助手手写 3–5 张卡，跑 20+ 回合，记录痛点；把本文改成定稿 | 小 | 一份「哪里不够用」的清单；§14 有答案 |
| **1. 角色卡 + 单角色场景** | `agents.rpJson`、`conversations.sceneJson`（migration v23）；卡渲染纯函数；编辑器 + JSON 导入；新建场景流程 + 开场白；投影接入 `buildWireHistory`；采样参数贯通；工具默认 None；demo 脚本；单测 | 中 | 无密钥 demo 能建场景、收到角色回复、重掷/回退可用；真机一家 provider 验证；手机/平板截图 |
| **2. 记忆** | 世界书（纯函数 + 预算 + UI）；场景简报（自动/手动，记账，可查看/重建，熔断）；笔记字段 | 中 | 50+ 回合不爆上下文；简报改动可解释；每回合成本可见 |
| **3. 多角色** | `messages.speakerId`（migration）；宿主编排；顺序规则；每角色模型；重掷/失败语义；成本披露与上限 | 大 | 2–3 角色场景可跑；停止/错误/重试不串；费用按次记账 |
| **4. 打磨** | PNG 卡导入/导出、角色库、OOC 视觉、语音朗读、场景模板、带说话人的 Markdown 导出 | 小步 | 各自带测试与文档 |

依赖：Phase 1 是地基；Phase 2 可与 Phase 1 并行设计但落地在其后；Phase 3 必须等
Phase 1 的投影稳定，否则多角色的上下文形状会返工。

## 12. 测试与验收

- **纯函数**：卡渲染、世界书命中、投影确定性（同样输入 → 同样请求）、前缀稳定性
  （同场景相邻回合的静态段逐字相同）、预算裁剪。放 plain-JVM 模块，和
  `:core:engine`/`:core:ai` 的测试同层。
- **迁移**：v22 → v23 的 `MigrationTest`（现有模式）。
- **demo**：`DemoProvider` 加一个 RP 标记（例如 system 含角色卡标记时回一段旁白+对白），
  无密钥验证流式渲染和重掷。
- **设备**：手机 360×640、平板 1024×768 实际截图；不要在流内状态上依赖 adb 采样
  （`AGENTS.md` 已说明这是不可观测的）。
- **真实服务**：至少一家 provider 跑通开场白、重掷、回退、长场景；只验证一次，
  写进文档而不是每次 CI 花钱。
- **必须证明不变量**：RP 场景的工具集为空；卡/简报不能改工具/审批/SSH；没有新网络路径。

## 13. 被否决 / 暂不做

- **工作区文件当卡/场景**（原判断，2026-11-26 部分推翻）：最初拒绝是因为"不可发现、
  不能校验、`AGENTS.md` 只 pin 一次"。2026-11-26 的决定把**资料源**放到工作区文件：
  建场景时用文件夹选择器发现并校验，场景创建时快照冻结（所以旧对话不受文件变化影响），
  格式说明改为 `rp_format`/`rp_validate` 两个工具而不是 `AGENTS.md`。这条仍拒绝的是
  "卡库只存在于工作区、没有发现/校验/冻结"的旧形态；Phase 1（从文件建场景）尚未实现。
- **新增「RP 模式」权限档或全局开关**：违反 §1.1；RP 是内容配置，不是能力。
- **角色自动对聊**：花钱不可控，且要自动回合循环，另做设计。
- **RAG / 向量记忆**：第一版不做；简报 + 世界书已能覆盖大部分长场景。
- **云端角色库 / 分享**：需要服务端、账号与隐私设计，当前产品明确单机。
- **PNG 卡导入**：解析 PNG tEXt 块本身不难，但第一版先把 JSON 和表单做对。
- **跨对话共享记忆**：`continuous-session.md` 明确列为非目标；RP 的「同一故事多个章节」
  属于另一个功能，需要单独的隐私与产品决定。

## 16. 决定记录（2026-11-25）

1. **不做个人助理（`continuous-session.md` §16.1 里的 B），本轮只做 RP。** RP 与个人助理
   在投影层是同一个机制，但个人助理的跨对话记忆是另一套作用域和写入规则；用户决定不做。
2. **形态：单角色、单会话。** 一次请求只有一个说话者；同一张角色卡可以开多段互不相干的
   场景，但场景之间不共享记忆。GM（一个模型扮演所有 NPC、做旁白）不需要单独实现：它就是
   一张写着 GM 规则的单角色卡。多角色（§7）不在本轮，`messages.speakerId` 与每回合 N 次
   调用都不做。
3. **迁移是 v23 → v24**（原文 §4.1 写的 v22 → v23 已过时；持续会话占了 23）。
   `agents.rpJson` + `conversations.sceneJson`，两列都是 `TEXT NOT NULL DEFAULT ''`，
   空串表示不是角色卡/场景。
4. **Phase 1 范围**：角色卡（§4.2 最小集 + 采样参数）、场景字段、开场白落成 assistant
   记录、新建场景流程（工具默认 `[]`，标题用角色名）、system 投影（规则 → 卡 → 场景 →
   持续指令 → 简报 → `AGENTS.md`）、每回合 `temperature`/`topP`/`maxTokens` 贯通到
   DeepSeek/OpenAI 兼容、Anthropic、Gemini、Responses、RP 场景的故事状态简报模板、
   DemoProvider 的离线场景脚本、`/ooc` 约定。
5. **不做**：世界书（Phase 2）、多角色、PNG 卡导入、SillyTavern JSON 导入（表单先做对，
   导入是后续小步）、自动上下文压缩之外的新记忆机制、RP 专用的全局开关或权限档。
6. **持续会话是默认载体**。新对话默认持续会话，所以场景也自动维护简报；为此简报提示词
   按「有没有角色卡」选故事状态模板。经典模式下场景照常工作，只是简报用通用模板。
7. **开场白的 wired 处理**：开场白落库为 assistant 记录（这是角色真的说过的话）；请求
   以 assistant 开头时，投影在 wire 上加一条**不落库**的起始 user 指令
   （`RoleplayPrompt.KICKOFF`），不伪造用户消息。
8. **工具**：建场景时写入显式的「无工具」（`ToolsColumn.NONE`，即 `"[]"`），不是空白、
   也不是锁死。用户仍可在会话工具清单里改，从下一回合生效；持续会话自带的只读 `recall`
   与能力缺口工具仍会出现，它们是记忆基础设施，不是场景选中的能力。
9. **实现落点（2026-11-25）**：`core/engine/.../roleplay/`（`RoleplayCard`/`RoleplayScene`、
   `RoleplayCodec`、`RoleplayLimits`、`RoleplayPrompt` 与单测）；`agents.rpJson` /
   `conversations.sceneJson`（v23→v24）与 `ConversationRepository.create` 的
   `tools`/`sceneJson`/`greeting` 参数；`RoleplayCardEditor`、`NewSceneDialog`、
   `SceneSettingsDialog`；`ChatViewModel` 的投影、起始行、采样透传、故事简报选择与
   `setScene`；`DemoProvider` 的场景脚本。开场白带 `finishReason = "stop"`，否则一个只有
   开场白的场景会被 `isInterruptedTurn` 判成中断并显示「继续」——这是设备验证时抓到的
   真实缺陷。角色卡可以在助手系统提示词为空时单独保存（`AgentDraft.canSave`）。
10. **2026-11-26：场景冻结 + 写作辅助工具（Phase 0 已实现）。** 场景创建时把助手提示词、
   名字和角色卡写成 `conversations.rpSnapshotJson`（schema v27）；投影读快照，编辑助手不再
   改写已经开始的场景；场景设定里的「重新读取角色卡与助手提示词」是唯一显式刷新入口。
   `rp_format` / `rp_validate` 两个辅助工具（`core/engine/.../roleplay/RoleplayTools.kt`）
   只随工作区文件能力出现；`rp_validate` 需要 `read_file`/`list_files`，纯场景保持空工具集。
   这是"工作区文件当 RP 资料源"的第一步：Phase 1（选工作区文件夹 → 校验 → 创建场景，
   不再依赖 `agents.rpJson`）尚未实现，见 `docs/proposals/rp-authoring-assistant.md`。
