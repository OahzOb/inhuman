# RP 工坊（内置 RP 工作区）— 评估与提案

> **状态：P0 已实现（2026-11-27），P0b 与 P1 未实现。**
> v2 采纳"这些额外功能只在一个内置 RP 工作区里出现"的方向，取代 v1 的"按助手勾选
> opt-in 工具"设计；v1 的方案保留在附录 A 作为记录。
> **P0 落地内容**：schema v28 `workspaces.kind`；首页常驻入口与新建入口（懒创建工坊）；
> 工坊里非场景对话由宿主附加 `rp_format`、`rp_validate`（需已有读工具）与
> `rp_create_scene`；场景提案卡与"创建并打开"（`RoleplaySceneCreator`，`tools="[]"`、
> 冻结快照、开场白、模型沿用当前对话、绑定工坊永久工作区）；"重新读取角色卡"按钮只在
> 实时助手有卡时显示；demo 模式用含 `scene` 的消息触发提案。P0b（引用旧对话）与 P1
> （社区卡来源/实时读取）未实现。
> 关联：`conversation-references.md`（把旧对话递给工坊助手）、`rp-authoring-assistant.md`、
> `roleplay.md`、`rp-formatting.md`、`docs/07-gotchas.md` A26/A30/A31、
> `docs/08-port-philosophy.md` §1.1/§1.2/§3.4（Q4）、`docs/11-conversation-tools.md`、
> `docs/13-product.md` 的「判断新功能该不该做」。

## 0. 结论先行

- **这个方向更好，建议采纳。** 把"额外功能"从"任意助手、任意工作区都能勾选"改成
  "只在**内置 RP 工坊**里出现"，在管理上更简单，而且**不需要新的权限语义**。
- 关键理由：这些功能**不是能力**。场景提案卡只是聊天里的一条数据（不写 DB、不联网、
  不执行），引用旧对话是用户手势产生的副本，`rp_format` 是常量文本，`rp_validate`
  只报结构。它们和 `recall`、`rp_format` 一样，是**宿主按条件附加的辅助工具**；
  能力仍然只来自"助手/对话的工具清单"里那些真正能读文件、能联网、能执行的东西。
- 具体形态：新增一种工作区类型（`workspaces.kind = "roleplay"`，schema v28），app 内置一个
  **RP 工坊**（首次使用时懒创建，首页"新建"里一个入口）。工坊里的**非角色扮演场景**对话
  自动获得 `rp_format`、`rp_create_scene`（提案卡）和（有读取工具时的）`rp_validate`；
  工坊同时是 RP 资料和"由提案创建的场景"的**永久工作区**。角色扮演场景本身保持空工具集。
- **不是模式**：工作区类型是数据属性（像永久/临时），只决定宿主附加哪些**零能力**辅助，
  不产生可提升的权限层级；模型没有创建/标记工作区的工具，所以它不能把自己搬进工坊。
  进入工坊是用户动作。
- 三个管理上的收益：
  1. 不用给每个助手勾选任何新工具——助手编辑器、会话工具 sheet、审批规则表、
     `unavailable_tools` 都不出现这些名字；工具目录也不增加条目（仍是 44 个）。
  2. 用户只需要记住一个地方：**要 agent 帮你做 RP 的事，去 RP 工坊聊**。
  3. 工坊是永久工作区：资料不会随对话删除，提案创建的场景也绑定它——v1 里"场景用临时
     工作区、资料容易丢"的问题一并解决。
- 规模：P0（工坊 + 提案卡 + 创建并打开）≈ **5–7 天**（含 v28 迁移与双尺寸验证），
  已实现；P0b（引用旧对话副本）≈ 2–3 天；P1（社区卡/资料文件、实时读取）≈ 4–6 天。
- 明确不做：agent 自己创建/切换工作区、agent 改工具/审批/SSH/下载/服务商、自动跑回合、
  自动把历史灌进新场景、跨对话自动记忆。

## 1. 需求与上一版设计的问题

### 1.1 原需求

> "我需要 agent 能全权掌控，用户只需要和 agent 聊天，然后 agent 自己创建，配置，
> 用户只需要操作选择角色卡和资料，甚至 agent 可以帮用户开个对话，用户直接点进去聊。"

拆成三个动作：

| # | 动作 | 今天 | agent 能做吗 |
|---|---|---|---|
| A | 创建/配置内容：写卡、写场景、整理素材 | 工作区文件 + `rp_format`/`rp_validate` | 能（把文件工具给它） |
| B | 选择角色卡和资料 | 工作区 `rp/<story>/`、Files 导入、分享 | 不能替用户去设备里找（结构限制） |
| C | 开一场对话，用户点进去聊 | `NewSceneDialog` + `repository.create` | **不能 —— 要补的就是这一下** |

B 不能消除的部分：agent 没有设备文件系统访问权。用户必须把卡/资料"交给"它（Files
导入、分享、卡编辑器），能优化的是这一步的体验（P1），不是让 agent 浏览手机存储。

### 1.2 v1 设计与其管理问题

v1 的做法：把 `rp_create_scene` 做成 `ToolCatalog` 里的 `optIn` 条目，用户**给每个想用的
助手勾选**；提案卡 + 一键创建，另外"引用另一段对话"作为输入框动作。

安全上没问题，但管理上确实有你说的毛病：

- **任意助手 × 任意工作区**都能出现这些功能，用户要记住"哪个助手勾过"，还得为每个助手配置；
- 助手编辑器、会话工具 sheet、审批规则表、能力缺口报告里都会多出 RP 专用条目；
- 工具目录从 44 变 45，以后每加一个 RP 动作就再变一次；
- 场景产物没有天然的永久工作区：v1 的 P0 用临时工作区，资料和场景不在一起。

### 1.3 新判断：按"运行环境"收口，而不是按助手发权限

把这几件事分成三类，界线就清楚了：

| 类别 | 例子 | 谁能决定 | 本次怎么处理 |
|---|---|---|---|
| **能力**（能读文件、能联网、能执行） | 文件工具、SSH、下载、B 站、媒体 | 用户，经助手/对话的工具清单；能力边界不可提升 | **不变**：仍由助手/对话决定，工坊不额外给 |
| **内容** | 角色卡、场景、素材、开场白 | 可以让 agent 决定；代码不读它（A26） | **不变**：让 agent 写 |
| **宿主辅助**（无能力） | `recall`、`rp_format`、`rp_validate`、**场景提案卡** | 宿主按条件附加，**不进用户选择、不进审批** | **只在工坊里附加**；新增提案工具 |
| **用户手势动作** | 导入文件、导出、**引用一段对话** | 只有用户能做 | 只在工坊的输入框里提供"引用对话" |

这就是为什么"按工作区收口"不需要新例外：被收口的那些是第三类，它们本来就不具备能力。
而真正有能力的工具仍走原来的路（助手是 ceiling、对话复制、用户改、下一回合生效）。

## 2. 为什么"工作区类型"不是一种模式

`docs/08-port-philosophy.md` 拒绝的是**可提升的权限层级**和"要更多权限"的入口。工作区类型

- 是**数据属性**（和"永久/临时"同类，`WorkspaceEntity.isPermanent` 已经是这种形状），
  不是权限档；
- 只决定宿主附加哪些**零能力**辅助；不改变工具清单内容、审批、SSH/下载授权、工作区边界；
- **模型没有创建/标记工作区的工具**，也不能把对话搬进工坊——进入工坊是用户点开入口
  或用户在创建对话时选工作区，是用户手势；
- 即使模型说服自己"我要用 rp_create_scene"，它也只能提案；创建仍要用户点按钮，且创建的
  对话工具集是显式 `"[]"`。

对照 `docs/13-product.md` 的六问：

| 问题 | 回答 |
|---|---|
| 1. 是否扩大助手能碰到的东西？ | 否。辅助工具没有网络、没有工作区外读取、没有执行；文件工具仍由助手/对话决定 |
| 2. 是否引入"可以要更多权限"的入口？ | 否。没有权限层级；模型不能进入/创建工坊；不能改工具/授权 |
| 3. 是否可逆？ | 提案不点 = 无状态；创建后是普通对话，可删除；场景绑永久工作区，资料不随对话丢失 |
| 4. 用户能否自己验证？ | 能。工坊是可见的工作区（资料/对话/场景都在）；提案卡显示角色/场景/模型；场景设置可查快照 |
| 5. 是否只在桌面成立？ | 否，手机优先，入口在首页新建与工作区详情，复用现有列表/对话框 |
| 6. 是否用反复询问代替一次性披露？ | 否。一次"进入工坊"的选择即说明这里的助手会做什么；没有逐次确认 |

需要记录的边界一句话：

> **agent 可以在 RP 工坊里准备内容和一场对话；它不能改变任何对话能做什么，也不能离开
> 工坊去读别的对话（除非用户引用/共享给它）。**

不需要在 `docs/08` 增加第三/第四个例外：这不是出口（egress）、不是新数据路径、不是新执行
环境。它只是把已有的**无能力辅助**限定在一个产品区域里。

## 3. 推荐设计：RP 工坊（P0）

### 3.1 数据与入口

- **schema v28：** `workspaces` 加 `kind TEXT NOT NULL DEFAULT ''`；`kind = "roleplay"` 表示
  RP 工坊。迁移只加列，不创建行（不在迁移里做文件系统动作）。
- **内置一个：** `ensureWorkshop()` 查 `kind='roleplay'` 的工作区；没有就
  `repository.createWorkspace("RP 工坊")` 再写入 kind（懒创建，首次点入口时发生）。
  app 保证最多一个；用户不能通过 UI 把别的工作区改成工坊（P2 再考虑"收养现有工作区"）。
- **入口：** 首页"新建"表里加一项 **RP 工坊**（图标，一行说明"让助手帮你做角色卡和场景"），
  首页对话列表上方另有一个**常驻入口**（一行：名称 + 说明 + 箭头，手机和平板都显示）。
  点击后：
  - 工坊还没有对话 → 直接进入"新建对话"流程（工作区预设为工坊，走现有助手选择器）；
  - 工坊已有对话 → 打开工坊中心（复用 `WorkspaceDetailScreen` 的工作区详情：对话列表 +
    文件 + 新建对话），并显示工坊说明与空态文案。
  - Workspaces 列表给内置工坊一个小标记（P2 可置顶）。
- **删除/改名：** 改名允许（只改显示名）。删除复用永久工作区规则：有对话时
  `deleteWorkspace` 拒绝删除（`ConversationRepository.kt:387-394`）；用户清空对话后可以删，
  入口下次会重新建一个空工坊。这样资料不会因为误删工作区而静默消失。
- **备份：** 工作区行本来就是备份的一部分，`kind` 随之恢复；备份恢复后入口仍指向同一个工坊。

### 3.2 哪些对话获得辅助工具

条件：`conversation.workspaceId` 指向 `kind='roleplay'` 的工作区，**且**这个对话不是角色
扮演场景（`roleplayActive == false`，即没有场景、助手也没有角色卡）。

- `rp_format`：**无条件附加**。它是常量格式文本，不需要文件能力；有了它，工坊对话即使没有
  文件工具也能现场写卡（提案卡里传 `card`）。
- `rp_validate`：仅当对话已有 `read_file` 或 `list_files` 时附加——它读工作区文件，
  不能成为用户没授予的读路径（沿用 `RoleplayToolsPlan.kt:22-34` 的规则）。
- `rp_create_scene`：附加；它只校验并返回提案，用户点卡片才创建（见 §3.3）。
- **角色扮演场景对话**（工坊里创建的角色扮演场景）：保持显式空工具集 `"[]"`，
  不附加以上任何辅助——故事里不应该出现"帮我建场景"的工具。
- **不进任何用户可见的选择面：** 三个名字不加入 `ToolCatalog`，因此不出现在助手编辑器、
  会话工具 sheet、审批规则表、`unavailable_tools`，工具总数仍是 44。它们由
  `ChatViewModel.buildTools` 按条件追加（与 `recall`/`rp_format` 同一种机制，
  `ChatViewModel.kt:6363-6381`）。
- **行为变更（有意）：** `rp_format`/`rp_validate` 从"任意有文件工具的对话"改为
  "只在工坊对话"。这是对 `rp-authoring-assistant.md` 早期决定（§2.4/§5）的修订：
  RP 资料写作收口到工坊，普通对话不再带 RP 提示。实现时同一提交更新
  `rp-authoring-assistant.md`、`docs/06`、`docs/07` A30、`docs/11`、`docs/13`。

### 3.3 提案卡与"创建并打开"

这是 v1 的核心交互，保持不变，只是作用域变了：

1. 用户在工坊对话里说"用《雨夜酒吧》那张卡开个故事，我要当常客"。
2. agent 调 `rp_create_scene`：
   - 参数（二选一来源）：`character`（现有助手名，取它的 `rpJson`）或 `card`（agent 现写，
     字段同 `rp_format`）；可选 `scene`；可选 `title`（默认卡名）。
   - 校验：`RoleplayCodec` + `RoleplayLimits`（+ 必要时 `RoleplayValidator`）；
     失败返回字段级错误，不产出提案。
   - 返回：`content` 是结构化提案（JSON），`persistedContent` 是一行摘要
     （"已准备场景提案，等待用户点击创建；不要声称已经创建"）。
3. 聊天里渲染**场景提案卡**：角色名、场景摘要、模型（沿用当前对话）、
   **[ 创建并打开 ]** / **[ 不要 ]**。
4. 用户点击后（app 动作，不是工具执行）：
   - 用同一套 codec/validator 再校验一次；
   - `repository.create(...)`：
     - `workspaceId = 当前工坊工作区`（**永久**；场景和资料住在一起）；
     - `tools = emptyList()` → 显式 `"[]"`（不是 `null`，见 A26）；
     - `rpSnapshotJson`（来源助手 prompt + 卡，或 inline 卡的 prompt 为空串）；
     - `greeting`（同一事务写入 assistant 根消息）；
     - `sceneJson`（空白归一化为 `"{}"`）；
     - provider/model/reasoning/thinking **沿用当前对话**（需要给
       `repository.create` 加可选覆盖参数，现在只从 `agent` 复制，
       `ConversationRepository.kt:619-622`）；
     - sessionMode 沿用用户新对话偏好。
   - 成功后直接 `onOpenConversation(id)` 进入场景，开场白已经在。
5. 不点 → 什么都没有发生。提案只是聊天里的一条结果，不写 DB、不建工作区。

**为什么不是"工具直接创建对话"：** 进入对话本来就要点一下；"提案 + 点一下同时创建并打开"
和"先创建、再点开"点击次数相同，但前者没有无人确认的 app 状态，不需要讨论回滚语义，
也不会留下垃圾对话。

### 3.4 工坊里的资料、场景与文件工具

- 工坊工作区就是 RP 资料的家：`rp/<story>/card.json` + 可选 `scene.json`；卡编辑器
  "导出到工作区"、Files 导入、分享进来都还是原来的路径。
- 由提案创建的场景绑定工坊工作区（永久）：删场景对话不删资料；改资料只影响**新**场景
  （已建场景的 persona 冻结在 `rpSnapshotJson`，A30）。
- 文件工具仍然是**能力**，来自助手/对话选择：新建助手默认带
  `list_files/read_file/...`（`AgentRepository.kt:88-92`），所以默认工作流开箱可用；
  如果工坊对话的助手没有文件工具，agent 仍能现场写卡并提案（`card` 来源不需要文件），
  但读不了工坊里的资料和"引用副本"——界面需要在引用入口处提示这一点。
- 手工路径不变：`NewSceneDialog` 的"工作区资料"仍然接受**任意**永久工作区（工坊只是
  内置的那一个）；工坊是"更方便的默认家"，不是唯一合法路径。

### 3.5 不变量对照

| 约束 | 本设计怎么满足 |
|---|---|
| 没有 "full access"、能力不能提升（§1.1） | 没有权限等级/开关；工坊不新增任何能力；文件/SSH/下载/审批全部不变 |
| 能力边界一句话（§1.2） | 仍然成立：agent 只看见工作区；提案/引用都是用户给的；没有网络/执行 |
| 只有用户能改工具、没有 tool adds tools（`docs/11`） | 辅助工具不是"工具集"的一部分，不进 sheet；创建的场景写 `"[]"`；场景里的工具仍只能用户改 |
| RP 是内容不是能力（A26） | 卡/场景只进提示词；提案不写 DB；创建是用户点击后的 app 动作 |
| 助手是 ceiling、对话是复制 | 不变；文件工具仍来自助手/对话；辅助工具不读工作区以外 |
| 花钱必须显眼（§1.4） | 提案/创建不花请求；新场景沿用当前对话模型；第一次花钱是用户发消息 |
| 回合/并发（Q4） | 不启动回合、不并行；只是当前回合里的串行工具调用 + 一次用户触发的创建 |
| 可验证 | 工坊可见、提案卡可见、场景设置可查；没有被隐藏的 app 状态 |
| 可逆 | 提案不点=无；创建后可删除；场景绑永久工作区所以资料不丢 |
| 诊断/备份（`docs/10`、`docs/04`） | 只记标题/条数/长度；v28 列随 DB 备份 |

## 5. P0b：引用旧对话（详见 `conversation-references.md`）

用户带着一段聊了很久的 RP 来要求改卡/开续集时，工坊需要看到那段对话：

- **复制方案（先做）：** 工坊输入框的附件菜单加"引用一段对话…"→ 选一段其他对话 →
  app 生成净化 Markdown 副本写入工坊工作区 `references/…` → 消息里带相对路径 →
  agent 用文件工具分块读。副本是快照，原件不动；删 chip 即删副本。
- 作用域：**只在工坊的输入框里提供**（保持"一个地方"的管理故事；以后要放开很容易）。
- 不做实时读取；实时读取（白名单 + `read_conversation` 工具）放 P1，且白名单建议放在
  **工坊级**（`workspaces.readableConversationsJson`），因为工坊就是管理单元。

## 6. P1：社区卡与资料、实时读取

1. **社区卡来源：** `rp_create_scene` 增加 `source`：工坊工作区里的 `rp/<story>/` 文件夹
   （`RoleplayStoryLoader`）、或原始卡文件 PNG/JSON/CHARX（`RoleplayCardImport`）；
   与 `rp_validate` 同一校验器；只接受工坊工作区内的路径，经 `SessionWorkspace.resolve`。
2. **资料投递：** 现在聊天附件只接受图片；P1 可加"资料文件"或继续用 Files 导入 +
   卡编辑器"导出到工作区"（已存在）。这是独立的小功能决定。
3. **实时读取：** 工坊级白名单 + `read_conversation` 工具（list/search/read，只读、
   分块、不读工具结果/推理/附件），勾选处披露"正文会随本对话请求发给服务商"。
   见 `conversation-references.md`。
4. **持久提案/已创建标记：** 重载后提案按钮仍可用、每工坊创建上限/来源标记；需要
   `conversations` 加列（v29）或快照标记。P0 接受"重载后按钮消失"。

## 7. P2 与不做

- **收养现有工作区**（把已有 permanent workspace 标成工坊）或多工坊：如果用户已经有资料在
  别的工作区，先可跨工作区复制进工坊；收养作为 P2 的便利功能。
- **助手创建/编辑**（仅内容字段、工具必须为空、模型由用户选）：需要单独决定是否有价值
  （场景快照已能承载角色，助手行的价值是跨场景复用 + 模型配置）。
- **场景内续集/改卡**：在场景对话里说"把这个角色改一下，开个续集"——需要场景里也有提案
  能力，或跨对话路由，P2。
- **不做：** agent 创建/标记/切换工作区；agent 改工具/审批/SSH/下载/服务商；自动跑回合；
  自动跨对话记忆；世界书/多角色（属于 `roleplay.md` Phase 2/3）。

## 8. 风险与失败模式

| 风险 | 说明 | 缓解 |
|---|---|---|
| 单工坊 = 单配额/单目录 | 所有故事共享 256 MB/5000 文件；资料多时可能拥挤 | 文件工具/配额照旧；P1 文档说明；P2 可收养/多工坊 |
| 工坊删不掉（有对话时） | 用户可能以为能删目录 | 复用永久工作区规则并明确提示；先删对话再删工作区 |
| 行为变更：普通对话失去 `rp_format`/`rp_validate` | 曾在任意工作区用 agent 写 RP 文件的用户会感到变化 | 发布说明 + 文档；手工 NewSceneDialog 路径不变；工坊是新的默认家 |
| 工坊对话用了带卡助手 | 该对话是角色扮演，辅助工具被隐藏，用户困惑 | 空态/选择器文案提示"工坊的搭建对话用普通助手"；或者 P2 允许场景内提案 |
| 助手没有文件工具 | 读不了资料/引用副本，但现场写卡和提案仍可用 | 引用入口提示"当前助手没有文件读取工具"；默认新建助手带文件工具 |
| 提案卡 token | 卡最多 16 KiB 进当次回合 | 只有提案那一回合；`persistedContent` 用摘要 |
| 提示注入 | 社区卡/RP 文本可能说"忽略之前的要求" | 提案/引用都标注只读资料；创建要用户点击；能力不变 |
| "重新读取角色卡"误点 | 实时助手无卡时会清空快照（文件夹/提案来源场景的风险） | 按钮条件改成"助手有可解码卡"；彻底方案是来源标记（P1/v29） |
| 重载后提案按钮消失 | 刷新/重进后卡片不可点 | P0 文案说明"点击前不会创建"；P1 持久化 |
| 入口发现性 | 用户不知道工坊在哪 | 新建表入口 + 工坊空态说明；P2 视情况在首页更显眼 |

## 附录 A：考虑过的 v1（按助手 opt-in），以及为什么没采用

v1：`rp_create_scene` 作为 `ToolCatalog` 的 `optIn` 条目，用户给每个助手勾选；提案卡 +
一键创建；引用旧对话作为通用输入框动作。

- 安全上可行（工具零能力、optIn 不进"全部"），但如果按 v1 走，管理上会出现：
  配置分散到每个助手；工具目录/审批表/工具清单长期增长；功能可能出现在任意工作区；
  场景产物没有天然永久工作区。
- v2 把"能力"和"宿主辅助"分开后，按工作区收口更简单，也不需要新增目录条目。
- 如果以后用户希望在某些普通工作区里也能用 RP 辅助，可以再评估"把该工作区设为工坊"，
  而不是重新引入按助手的工具开关。
