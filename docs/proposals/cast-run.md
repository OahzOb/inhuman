## 0. 结论先行

用户想的是：**主 agent 能按角色卡造出若干"扮演者"，接上世界书，在群聊里各自扮演角色，
完成一次测试**；用途不限于 RP。

判断：**可行**。技术上不需要移植 DSH 的子代理架构；需要的是一层
「人格化的模型调用 + 导演编排 + run 内转录」。真正的代价不在运行时，而在
**成本闸门、上下文投影、以及"模拟不是证据"** 这三件事上。

三个必须一起成立的结论：

1. **演员没有通用能力**（无通用工具、无审批、无文件、无网络）；最多加一个宿主提供的只读世界书查询工具（§3.3.1）。否则"角色卡 + 通用工具"就是注入通道；
2. **一场 run 的请求数在开始前算给用户看，并且有硬上限**；
3. **主对话的"一个说话者"v1 不动**；群聊只存在于 run 内部。

## 1. 需求记录

### 1.1 用户原始想法（2026-11-27）

- 用户可以要求 agent 用自己写的角色卡，创建一个 subagent 扮演某个角色，用于测试；
- 接上之前讨论过的**世界书**；
- **群聊**（group chat）；
- agent 可以创建**多个** subagent 扮演**多个**角色，来完成一次测试；
- **不限于 RP**。

用户同时说明不着急，先记录需求与可行性。

**2026-11-27 澄清（需求重心）：** 主要目的不是 RP，而是省去"用户复制 agent 的输出 →
手工配置 → 自己试 → 截图/粘贴回来"的中转：让 agent 代写**用户可配置的内容**
（提示词、角色卡、世界书、场景……），自己试跑、自己改，用户最后验收。范围是整个
app 的用户可配置内容，**不碰工具如何运行、权限、授权、密钥和全局设置**；
完整需求见 [authoring-rehearsal.md](authoring-rehearsal.md)。

### 1.2 想解决的场景

| 场景 | 谁演谁 | 产出 |
| --- | --- | --- |
| 角色卡/提示词自测 | 用户或 agent 写的卡，演员扮演卡里的角色；主 agent 扮演用户或旁观者 | 卡在哪些话上"出戏"、越界、串设定 |
| 模拟用户测助手 | 演员扮演不同性格的用户，主助手是被测对象 | 助手在哪些输入上失败、答非所问 |
| 对抗评审 | 演员是几个持不同立场的审阅者（安全、成本、体验） | 各自挑错，导演汇总 |
| 专家小组/辩论 | 演员是不同领域专家 | 多视角结论与分歧点 |
| 故事排练 | 多个角色自动或半自动对戏，用户旁观/插话 | 一段可回看的场景 |

共同点：**需要多个人格、各自独立的上下文、由一个导演统一调度，并且要能停下来。**
这正是 RP 多角色群聊、也是通用"模拟/评审"的同一个原语。

### 1.3 "功能不做限制"的三种读法

| 读法 | 含义 | 判断 |
| --- | --- | --- |
| **A. 用途不限制**（本文采用） | 机制通用：RP、模拟用户、评审、专家小组都用同一套；不做 RP 专属 | 可行，且是推荐方向 |
| **B. 能力不限制** | 给演员任意工具、文件、网络、审批 | **不做**。它会变成 DSH 式有工具子代理，必须重新回答 §1.1 的注入问题：角色卡是 untrusted 文本（导入的卡尤其），通用工具是真能力；两者相邻就是提示注入的落点。若真要做，那是另一条线（见 §2.4），不和演员共用约束 |
| **C. 窄能力：一个只读查询工具**（2026-11-27 方向） | 宿主提供、只读、没有 path/URL 参数、只查本场世界书条目 | 可行，见 §3.3.1。边界仍是一句话：**演员只能查这场模拟的设定条目，读不到你的文件、连不出网、不会执行任何东西** |

无论哪种读法，**预算必须有硬上限**：一场 4 人 × 3 轮就是 12 次付费请求，
没有上限的"功能开放"等于"用户没看时烧钱"。

### 1.4 首版非目标

- **无界自演**：角色之间无限自动对聊。`roleplay.md` §3 的 D 已判"不做"（花钱失控），本文只讨论它的**有界版本**（§4.2）；
- 演员带**通用**工具/审批/网络/文件（见 §1.3 B）；窄能力的只读世界书查询工具不在非目标里（§1.3 C、§3.3.1）；
- 自动跨对话记忆、向量检索（世界书已够用）；
- 把 run 当成回归测试或证据：模拟只能发现问题，不能证明没有问题；
- 演员输出直接进入主对话（见 §5）。

## 2. 术语与分层

### 2.1 四层，不是一个功能

| 层 | 是什么 | 能力 | 成本 | 现状 |
| --- | --- | --- | --- | --- |
| **导演** | 主对话里的 agent：定名单、轮次、顺序，读转录，给结论 | 会话现有工具 | 1× 起 | 缺（需要编排工具/计划卡） |
| **演员** | 人格卡 + 世界书命中 + 独立消息窗口；文本进、文本出 | 0 通用能力；最多一个宿主提供的只读查询工具（§3.3.1） | 每次发言 1 次请求（含按需查询时 2 次） | 缺（单说话人的角色卡已有） |
| **转录** | run 内多说话人消息与投影：谁看得见什么 | 无 | — | 缺（`roleplay.md` Phase 3 已设计 `messages.speakerId`） |
| **worker subagent** | 有工具、独立会话、结果回传的隔离执行体 | 父级工具集交集 | 1× 起 | 缺（Q4：0；若加，1 个串行不递归） |

**核心判断：用户描述的"subagent 扮演角色"需要的是"演员"，不是 worker subagent。**
两者的区别不是叫法，而是**有没有能力**和**要不要持久会话**。

### 2.2 导演、演员与转录的分工

- 导演只做三件事：把需求变成一份 **CastPlan**（名单、每人目标、轮次、模型）、
  按计划驱动发言、把转录汇总成一份结论。导演自己的工具集**不因这场 run 改变**。
- 演员只做一件事：拿到 host 拼好的 system（人格 + 命中的世界书 + 场景规则）和
  转录里它该看见的部分，输出一段发言。它没有通用工具，也没有审批可触发；
  如果这场 run 开了按需查询，它可以调用唯一的只读世界书查询工具（§3.3.1）。
- 转录只存在于 run 内部：不写入主对话的消息流，不进首页对话列表；
  导演读取它，用户在 run 卡片里展开查看。

### 2.3 为什么不是 DSH 的 subagent

DSH 的 `subagent` 是**完整 agent**：独立且持久的子会话、自己的工具与审批策略、
树形目录、名字与冷恢复、每棵树默认 8 个并发、深度默认 1、结束通知回父级。
它是给"隔离的任务执行"设计的，不是给"扮演一句台词"设计的。搬过来有三个直接坏处：

1. **把 untrusted 角色卡放到工具旁边**——这正是最需要避免的组合；
2. **过重**：演员只需要 N 个独立消息窗口 + host 拼 system，不需要可恢复会话、
   目录、收发消息、树；
3. **成本和并发模型不同**：DSH 的完成通知会唤醒父级；演员是一场 run 里的
   串行调用，不产生新回合。

可以借鉴的是它的**经验**：完成/失败要显式回传、失败停住不重跑、成本归到发起者；
不需要的是它的**架构**。

### 2.4 worker subagent 是另一条线

如果将来确实需要"子代理带工具去干活"（读工作区、跑 SSRF 守卫的抓取等），
它应当按 [08 Q4](../08-port-philosophy.md) 已经定下的形状走：**1 个、串行、
不递归、工具集取父级交集、内部审批一律自动拒绝**，并且和演员分开设计、
分开上限、分开 UI。不要因为都叫"子代理"就共用一套约束。

## 3. 可行性分析

### 3.1 运行时：复用同一个 `ChatEngine`，不新增回合循环

一场 run 是**父回合里的 N 次串行调用**：父回合照常持有 `TurnConcurrency` 的一个名额
（[06-agent-loop-ui.md](../06-agent-loop-ui.md) "Concurrency ceilings" 不变），
`isStreaming` 仍是每对话一个回合；演员调用不是新回合，不经过 `send`，
不产生独立的 `TurnStatus` 通知。Stop 取消父回合 → 取消正在跑的演员调用 → 整场结束。

所需改动只在新的一层（`CastRunner` 之类的 host 组件）：构造每个演员的请求、
串行调用、收发言、写转录、判停。**引擎的回合语义不用改**。

### 3.2 消息与存储

- run 需要持久化：计划、状态、每个演员的发言、花费、失败原因；
- 转录用多说话人消息（`speakerId` / run 内序号），**不写进主对话**；
- v1 不改主对话"一个对话一个说话者"，也不要求 `messages` 表承担多角色；
  run 的消息可以独立一张表，或在现有表上加 run 维度——这是实现期的选择，
  本文只确认**可行且不动主对话语义**；
- `roleplay.md` Phase 3 的 `messages.speakerId` 是"用户参与的群聊"需要的；
  演员 run 是它的子集，先做 run 不会堵死 Phase 3。

### 3.3 世界书

[roleplay.md](roleplay.md) §6.1 已经设计过：条目 = 关键词 + 内容 + 位置 + 顺序 + 预算；
每回合按最近消息做**确定性的关键词命中**，纯函数、可测试；超出预算按顺序截断并说明；
第一版不做 embedding。演员版只是把"注入给主助手"换成"由 host 为每个演员渲染"。
**纯内容、不改变能力、成本可忽略**，是目前最确定、最便宜的一块。

注意现状：外部角色卡导入**故意不导世界书**（只报告条数），
见 [rp-formatting.md](rp-formatting.md) §9；世界书要么用户/agent 在工作区里写，
要么在应用内编辑，二选一需要产品决定（§7）。

#### 3.3.1 程序化命中 + 按需查询（2026-11-27 方向）

两者共用同一份条目数据，分工不同：

| | 程序化命中（主路径） | 按需查询（补充） |
| --- | --- | --- |
| 谁发起 | 宿主，每次演员发言前 | 演员自己决定 |
| 匹配依据 | 这个演员能听见的转录里的关键词 | 演员自己写的查询词 |
| 成本 | 只付被注入条目的 token | 多一次工具往返（≈2 次请求） |
| 确定性 | 完全确定、可测试 | 取决于模型判断 |
| 覆盖范围 | 最常见、最显而易见的条目 | 关键词没出现、或演员要主动核对的条目 |

- **工具只有一个**：`lookup_world(query)`，返回命中的条目（id、标题、正文），
  top-k 与返回长度都有上限；没有 path/URL 参数，不能读文件、不能联网、不能执行。
  它不属于 `ToolCatalog`，不出现在任何选择器里，只在 run 的 engine 配置里注册
  （和 `recall` 同一种 host 追加方式）。
- **同源**：查询工具必须复用自动命中用的同一份条目数据和同一套匹配/可见性规则；
  不能另建索引、不能通配或枚举（空查询拒绝），否则它会慢慢长成一个通用文件读取器。
- **定义稳定**：工具 schema 在一场 run 内不变，保持请求前缀稳定；工具定义一变，
  该演员之前的前缀就作废。
- **可见性过滤**：条目带 `visibility`（public / 私有给某个演员 / 仅导演）。
  程序化命中和查询工具都按当前演员过滤——没有这一层，演员一句"凶手是谁"
  就能查到 GM 秘密，非对称信息反而要靠它。
- **去重**：本次已经自动注入的条目，查询结果标注"已在上下文中"，避免重复 token。
- **上限**：建议每演员每轮最多 1 次查询、全场最多 6 次，并计入 CastPlan 的
  预计请求数；一场 run 的预算按"演员发言 + 查询往返 + 导演"合计。
- **审计**：每次查询在转录里留一条工具行（"小红查了 世界书·时间线"），
  用户能看出演员是"本来就知道"还是"临时查的"。
- **不是能力例外**：它不联网、不写、不执行、不带凭据，读的是用户/导演交给
  这场 run 的内容，所以 §1.2 的能力句子不受影响（见 §4.4）。

### 3.4 投影：每个演员看见什么

这是整个功能最需要设计的部分，也是可行的关键：

- 演员 A 看到：人格卡 + 命中的世界书 + 场景规则 + 转录中"它能听见"的发言；
- 演员 A **看不到**：导演的私有指令（"你要在第三轮露出破绽"）、其他演员的人格卡、
  主对话的历史；
- 导演看到：完整转录 + 自己的计划；它给用户的结论必须标明是模拟；
- 用户看到：run 卡片（名单、轮次、进度、花费）和可展开的转录。

结论：**投影是纯函数**（输入 run 状态 → 每个演员的 system + messages），
可以在 JVM 上测试，不需要设备。前缀稳定性也要照顾：同一演员的 system
在一场 run 内不应变化，否则每次发言都是冷请求（成本上升）。

### 3.5 UI

- **CastPlan 卡**：名单（卡名/目标/模型）、轮次、**预计请求数**、开始/取消；
- 运行中：一行进度（"第 2 轮 · 小红正在说…"）与 Stop；不把 N 个演员的流式
  都铺到聊天页；
- 结果卡：导演结论 + 每人转写可展开；
- 窗口比例按 `AGENTS.md` 的要求在 360×640、1024×768 等比例实跑。

### 3.6 成本与延迟

| 配置 | 演员请求 | +导演 | 串行耗时（粗估） |
| --- | --- | --- | --- |
| 2 人 × 2 轮 | 4 | 1 | 20–40 s |
| 3 人 × 2 轮 | 6 | 1 | 30–90 s |
| 3 人 × 3 轮 | 9 | 1 | 45–150 s |

- 每次演员调用都是一次普通付费请求；按 run 记账（现有 usage 体系可复用）；
- **按需查询不在上表内**：每次查询 ≈ 2 次请求（模型发起调用 + 带结果继续），
  所以 3 人 × 2 轮、每人每轮查一次就是 12 次演员请求而不是 6 次；查询必须计入
  计划卡的预计请求数，并按 §3.3.1 的上限封顶；
- 必须能 Stop；超时/失败不能自动重试整场；
- 建议上限写死：**演员 ≤ 4、轮次 ≤ 3、每场演员发言总数 ≤ 12（4×3），导演的汇总请求另计**；
  这些数字可调也只能往下调，另议。

### 3.7 Android 生命周期

- run 属于父回合，沿用现有前台服务与通知；**不新增 Service、不新增 WorkManager**；
- 用户离开 Activity、进程被杀：当前 run 取消，已落库的部分转录保留，**不自动续跑**——
  与 [08 Q3](../08-port-philosophy.md) 的既有答案一致；
- 屏幕不可见时是否允许 run 继续，取决于之后对"自动花费"的决定（目前 maintenance
  只在可见时花钱；run 是用户点开始的任务，可参照 goal 的讨论另定）。

### 3.8 失败与取消

- 某个演员调用失败：**停在该演员**并说明已说出的部分，不重跑整场；
- 用户 Stop：取消当前调用与剩余轮次，保留转录，状态标为已中断；
- 导演最后一步失败：保留转录，报告"结论未生成"；
- 这些语义与 `roleplay.md` Phase 3 的多角色失败规则一致，不需要新概念。

## 4. 与现有决定的关系

### 4.1 Q4 不变，但要补一条预算

[08 Q4](../08-port-philosophy.md) 的结论是"工具 1、进程 2、子代理 0；若加子代理仍是
1 个、串行、不递归"。**演员不是子代理**（没有通用工具、无审批、无会话可恢复），
不改变这条；但"一个回合内串行 N 次模型调用"是一个新的**性能预算**，
按 §3.1 的原则（安全边界不可协商、性能预算可调）应当有明确上限，
建议在 Q4 或 `06` 的并发上限表里补一句。

### 4.2 `roleplay.md` 的 D 需要改判

`roleplay.md` §3 把"角色自动对聊（用户旁观，角色之间自己演）"标为不做，
理由是**花钱失控**。本文的用例是它的**有界版本**：

> 不做**无界**自演；做**有界 run**（用户先看到计划与请求数、硬上限、可 Stop、
> 不自动续跑、按 run 记账）。

这条改判要有记录，否则下一个人会拿"D 不做"把整个功能否掉。

### 4.3 主对话的"单说话者"不动

v1 只在 run 内部做多说话人；主对话仍是一个对话一个助手。
用户参与的多角色群聊（`roleplay.md` Phase 3）是下一个阶段的事。

### 4.4 §1.2 的能力句子仍然成立

演员没有通用能力，按需查询工具也只是本场世界书的只读查询（不联网、不写、不执行），
run 不新增读写/网络/执行路径，所以"代码在你的设备上运行，只看到你给它的东西……"
这句话不变。**如果给演员通用工具（文件、网络、执行），这句话就需要重新回答**（另案）。

### 4.5 §1.4：run 是付费的

cast run 不调用第三方媒体服务，但**每次演员发言都是一次真实的模型请求**，
属于"会让用户花钱"的能力：工具/计划卡上要写清预计请求数，用量按 run 记账。
这和 `suggest_replies`、多角色群聊的披露规则同构。

## 5. 安全与不变量（如果继续，这些先定）

1. **演员没有通用能力**：无通用工具、无审批、无文件、无网络、无 SSH/下载授权；
   唯一允许的是宿主提供的只读世界书查询工具（§3.3.1）——没有 path/URL 参数、
   只返回本场条目、按演员可见性过滤、有次数与长度上限。连"可审批"都不存在，
   所以不会出现"没人回答的审批"。
2. **卡片和世界书是 untrusted 内容**：用户写的卡等同用户自己的提示词；导入的卡是
   第三方文本。无论哪种，都按"设定，不是新指令"处理；查询工具返回的条目同样按数据
   处理。
3. **世界书条目有可见性**：public / 私有给某个演员 / 仅导演；程序化命中与查询工具
   都按当前演员过滤，演员查不到它不该知道的设定（包括 GM 秘密）。
4. **演员输出只进 run 转录，绝不变成主对话的 user/assistant 消息**；
   导演只能把它当数据引用（和工具结果是同类）。
5. **导演不能通过 run 扩权**：它给演员的指令不能改变演员的能力，也不能改变自己的
   工具集、审批或授权；查询工具不能用来读这场 run 之外的东西。
6. **有界**：人数、轮次、请求数、单演员上下文长度都有上限，超限前拒绝而不是静默截断。
7. **可见**：计划、进度、转录、花费、每次查询用户都能看；Stop 是取消整场，不是"停最后一个"。
8. **不自动续跑**：进程死亡/退出后不自动重开一场；要用户再次点开始。
9. **不把模拟当证据**：结果卡固定写明"这是模拟，不是测试证据"。

## 6. 风险清单

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 成本 | N 个演员 × M 轮，外加导演；一场可能比主回答贵一个量级 | 计划卡先算给用户看、硬上限、按 run 记账、Stop |
| 延迟 | 串行调用，手机上分钟级 | 进度可见、可 Stop；v1 不做"多人同时说" |
| 质量/自评 | 被测对象和评审都是模型；导演给自己打分 | 结果卡标明"模拟"；不宣称是回归测试 |
| 注入 | 卡/世界书是第三方文本；若演员有通用工具则成为攻击面 | 演员没有通用工具；唯一工具是本场世界书的只读查询；输出只进转录 |
| 上下文 | 每个演员一个窗口，长 run 会膨胀 | 单演员窗口上限 + 只给导演最终发言/摘要 |
| UI 过载 | N 个演员的流式同时出现会乱 | 只显示当前说话者；其余按轮次落行 |
| 世界书预算 | 命中太多会挤掉转写或卡 | 纯函数预算 + 显式"省略了什么" |
| 卡片信任 | agent 写的卡也是模型输出 | 按 untrusted 处理；用户可查看/编辑 |
| 模型差异 | 全场一个模型 vs 每演员一个模型影响成本与体验 | v1 全场一个（继承会话模型），另议 |

## 7. 待用户拍板的问题

1. **演员能力**：~~0 工具 vs 只读工具~~ **方向（2026-11-27）：程序化命中 + 一个只读查询工具**。
   剩余待定：查询默认打开还是 CastPlan 里可关、每演员每轮与全场查询上限的具体数字。
2. **谁发起 run**：用户点 CastPlan 上的"开始"（推荐），还是 agent 可以自行开跑？
3. **形态**：v1 只做 run 内私有转录（推荐），还是直接做用户参与的多角色群聊？
4. **世界书存哪**：工作区文件（可编辑、可复用、可进工坊，推荐）还是应用内编辑器？
5. **模型**：全场一个（继承会话模型，推荐），还是每个演员可选？
6. **上限**：演员人数、轮次、单场请求数的具体数字。
7. **被测试对象**：测试当前助手，还是允许指定另一个 provider/model 作为被测方？
8. **后台**：屏幕不可见时是否继续跑（参照 goal 的同类问题）。

## 8. 结论与建议顺序

**可行**。最大的工程不是"跑多个模型"，而是**投影**（每个演员看什么、导演看什么）
和**成本闸门**；两者都可以先设计成纯函数/纯策略，在 JVM 上测。

建议顺序（每步单独可用，不依赖后一步）：

1. **世界书 + 单角色**（`roleplay.md` Phase 2）：最便宜、独立有用、不引入新循环；
   先只做**程序化命中**（纯函数、可测试），把确定性和预算打牢；
2. **演员 runner**：CastPlan + 点按开始、run 卡片——用户想法的核心；先跑纯程序化命中版；
3. **按需查询工具**（`lookup_world`）：在演员 runner 上追加，纳入请求预算与可见性过滤；
4. **用户参与的多角色群聊**（`roleplay.md` Phase 3）；
5. **有工具 worker subagent**（Q4 形状，另一条线）。

程序化命中与按需查询是同一份条目数据的两种读法：先用前者建立确定性与测试基线，
再把后者作为补充加上去——不要一开始就让模型自己决定一切。

如果继续，下一步是把上面的问题（§7）答完，再写实现计划与验收标准；
本文不替它们做决定。
